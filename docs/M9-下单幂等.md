# M9 · 下单幂等

> 目标：同一个「购买意图」重复提交，只产生一笔订单、只扣一次库存。
>
> 这一篇的重点不是"加了个Redis锁"，而是**为什么单一方案都不够**，
> 以及**为什么兜底逻辑必须写在事务外层**——后者是 Spring 里最容易踩且最难查的一类坑。

---

## 一、问题：现有防护挡不住重复下单

下单方法里已经有一道防线：

```java
UPDATE product SET stock = stock - #{qty}, sales = sales + #{qty}
WHERE id = #{id} AND stock >= #{qty}
```

它解决的是**超卖**——100 件库存不会卖出 101 件。

但它解决不了**重复下单**：

| 场景 | 防超卖能不能挡 |
|---|---|
| 用户在结算页手抖点了两次 | ❌ 两次都合法，扣两次库存 |
| 前端请求超时（15s），用户点重试，其实第一次已经成功 | ❌ 更隐蔽，用户完全无感知 |
| 用户在两个标签页同时提交 | ❌ |

结果：两笔订单、两次扣库存、两份运费。用户来投诉时，你只能手动退款。

> 「防超卖」和「幂等」是两个不同的问题。前者是**并发正确性**，后者是**语义去重**。
> 面试时能把这两者分开讲，是很明显的加分点。

---

## 二、方案：两层，各管一段

```
客户端生成 requestId
        │
        ▼
┌───────────────────────────────────────┐
│ 第一层：Redis SETNX                    │
│ 挡住 99% 的重复请求                     │
│ 命中 → 直接回放上次结果，事务都不开      │
└───────────────────────────────────────┘
        │ 未命中（首次）
        ▼
┌───────────────────────────────────────┐
│ 业务事务：扣库存 → 建单 → 建明细 → 清车 │
│ INSERT 时带 request_id                 │
└───────────────────────────────────────┘
        │ 并发穿过第一层时
        ▼
┌───────────────────────────────────────┐
│ 第二层：唯一索引 uk_user_request        │
│ INSERT 撞索引 → 回滚 → 反查已有订单返回  │
└───────────────────────────────────────┘
```

### 为什么不能只用 Redis

Redis 是外部依赖。它挂了、被 flush 了、key 过期了、或者两个请求恰好同时 SETNX 成功
（不可能，但 key 过期后重来就可能），幂等就失效了。

**幂等的保证必须落在数据层**，否则它只是"大部分时候有效"。

### 为什么不能只用唯一索引

技术上可行：让 INSERT 撞索引抛 `DuplicateKeyException`，捕获后返回已有订单。

但代价是每次重复请求都要完整跑一遍扣库存、插入、冲突、回滚。**重复请求走的是异常路径**，
正常路径零开销——听起来还行。

真正的问题是**代码结构**：`create()` 上有 `@Transactional`，异常在事务方法内抛出时，
Spring 已经把事务标记成 `rollback-only`。这时候你在这个方法里 `catch` 住它继续查库：

- 能查到数据（同一个连接，对方已提交）
- 但方法返回时事务提交会抛 `UnexpectedRollbackException`

所以 `catch` 必须放在**事务方法之外**。而 `OrderService` 内部自己调自己不走代理，
`@Transactional` 会失效——这就是为什么多了一个 `OrderCreateGuard` 类。

> 一句话总结：**Redis 是为了快和体验（第二次请求不干活），唯一索引是为了对（数据层强保证）。**

## 三、实现要点

### 3.1 `OrderCreateGuard.create()`

```java
Boolean acquired = tryAcquire(key);           // SETNX key PROCESSING EX 30
if (FALSE.equals(acquired)) return replay(…); // 重复请求：回放上次结果
// acquired == null：Redis 挂了，降级为只靠唯一索引
try {
    OrderVO vo = orderService.create(userId, request);  // @Transactional 在这里面
    remember(key, vo.getId());                          // 改成订单ID，TTL 24h
    return vo;
} catch (DuplicateKeyException e) {
    return loadByRequestId(userId, requestId);          // 兜底：反查已有订单
} catch (RuntimeException e) {
    release(key);                                       // 业务失败，释放
    throw e;
}
```

三个 `catch` 分支各自对应一种真实情况，缺一不可。

### 3.2 为什么用 SETNX 而不是 GET + SET

```java
// ❌ 竞态：两个线程同时 get 到 null，同时 set，都认为自己抢到了
if (redis.get(key) == null) { redis.set(key, "PROCESSING"); ... }

// ✅ 判断和写入是一条原子命令，中间插不进任何客户端
redisTemplate.opsForValue().setIfAbsent(key, PROCESSING, LOCK_TTL)
```

和 M7 里用 Lua 取延迟任务是同一个道理：**需要原子性的地方，就别分两次调用。**

### 3.3 键里为什么带 userId

```java
String key = "order:idem:" + userId + ":" + requestId;
```

两个原因：

1. 不同用户的 requestId 互不影响（虽然 UUID 不会撞，但不能假设客户端守规矩）
2. 唯一索引也是 `(user_id, request_id)`，两层语义对齐

顺便做了格式校验 `^[A-Za-z0-9_-]{8,64}$`：不加的话，客户端可以传 `a:b` 把 key 拼串味，
或者传 10KB 的字符串撑爆索引。

### 3.4 为什么失败必须释放幂等键

不释放的后果：用户买 100 件，库存只有 10 件 → 400。他去改数量，再提交 → 还在 30 秒
的 TTL 内，被当成重复请求，返回 409「请勿重复提交」。

**用户被自己的失败请求挡住了**，只能干等半分钟。这是最容易被忽略、但用户体验最差的一种 bug。

### 3.5 PROCESSING 这个中间值为什么不能省

如果 SETNX 只写一个占位符 `1`，那重复请求就无法区分两种情况：

- 第一次**还在跑** → 应该让客户端稍等（409）
- 第一次**已经完成** → 应该把结果还给它（200 + 同一笔订单）

所以值有两个状态：`PROCESSING` → 订单 ID。

## 四、踩过的坑

### 4.1 唯一索引的前缀顺序

```sql
UNIQUE KEY uk_user_request (user_id, request_id)   -- ✅
UNIQUE KEY uk_request_user (request_id, user_id)   -- ❌
```

看起来两种都能保证唯一，但反过来的话：**A 用户用了 `abc`，B 用户就再也不能用 `abc`**。
UUID 虽然不会撞，但客户端的 ID 生成策略不该被服务端的数据结构绑架。

顺序正确时查询也能用上索引（查询条件永远带 `user_id`）。

### 4.2 加唯一索引前必须回填历史数据

`request_id` 是 `NOT NULL DEFAULT ''`。直接加索引的话，所有历史订单都是空字符串，
`(user_id, '')` 立刻冲突——**同一个用户只能留下一张历史订单，其余全部建索引失败**。

所以脚本里第二步是回填：

```sql
UPDATE orders SET request_id = CONCAT('legacy-', id) WHERE request_id = '';
```

用 `legacy-{id}` 保证每条不同，同时一眼能看出这是回填数据。

> 也考虑过允许 NULL（MySQL 唯一索引对 NULL 不去重）。但那样"漏传 requestId"的记录
> 会全部绕过约束，等于没有保护——不符合"数据层强保证"的初衷。宁可 NOT NULL 让漏传直接报错。

### 4.3 兜底 catch 必须在事务外层

这就是第二节说的那个坑。具体代码：

```java
// OrderService.create 有 @Transactional，异常从这里冒出来时事务已回滚
OrderVO vo = orderService.create(userId, request);
```

`OrderCreateGuard` 是个**独立的 Bean**，所以 `orderService.create(...)` 走的是代理，
事务正常生效；异常冒到 Guard 时，事务已经回滚干净，此时查库是干净的新事务。

如果图省事把幂等逻辑写在 `OrderService` 内部、自己调自己，`@Transactional` 会静默失效
（没有代理），扣库存和建订单就不在同一个事务里了——**这类 bug 平时测不出来，压测或
异常时才炸**。

### 4.4 `UID` 是 bash 只读变量

测试时写了 `UID=$(mysql -N -e "SELECT id FROM user …")`，赋值静默失败（Git Bash 里 UID
是进程 uid），导致 Redis key 拼错，测试"通过"了但根本没测到目标分支。

改成 `USER_ID` 才正常。**变量名撞了 shell 内置变量，赋值不会报错，只会给你一个错误的值。**

## 五、实测数据

测试环境：本地 MySQL 8 + Redis 5.0.14（Windows 服务），超时设默认 30 分钟。

### 5.1 同一 requestId 连续三次

| 次数 | 返回 | 订单号 |
|---|---|---|
| 1 | 200 | SO2124831123006529537（id 3777） |
| 2 | 200 | SO2124831123006529537 |
| 3 | 200 | SO2124831123006529537 |

商品 6：库存 `60 → 58`、销量 `430 → 432`（**只扣一次**）；数据库该 requestId 共 1 条记录。

### 5.2 不同 requestId

商品 7 下单两次 → 生成 3778 / 3779 两笔，库存 `498 → 496`。没有误拦。

### 5.3 10 并发同 requestId

```
业务 code 分布：10 × 200
订单号去重后：1 个
商品 8 库存：35 → 34（只扣一次）
数据库该 requestId：1 条
```

10 个请求全部拿到 200 和同一笔订单——第一个请求在几十毫秒内就完成了，
后面的都命中"结果已就绪"的回放分支。这说明**回放分支的体验比 409 好得多**。

### 5.4 首次仍在处理中（手动造 PROCESSING 状态）

```
HTTP 409  {"code":409,"message":"订单正在处理中，请勿重复提交"}
商品库存未变化
```

### 5.5 业务失败后重试

| 步骤 | 结果 |
|---|---|
| 买 99999 件 | 400「库存不足」 |
| 检查幂等键 | `exists = 0`（已释放） |
| 同一 requestId 改买 1 件 | 200，订单 3782 |
| 幂等键值 | `3782`，TTL 86400 |

### 5.6 停掉 Redis 再重复提交（最关键的一组）

```
第 1 次：200，订单 3783
第 2 次：200，订单 3783   ← 走的 DuplicateKeyException 兜底
商品 9 库存：149 → 147（只扣一次）
数据库该 requestId：1 条
```

Redis 完全不可用的情况下，幂等依然成立。这证明唯一索引不是"写在文档里的计划"，
而是真的在兜底。

### 5.7 唯一索引前缀语义

```sql
-- user_id=1 + 已有 requestId  → 插入成功（不同用户可复用）
-- user_id=5 + 已有 requestId  → Duplicate entry '5-idem-diff-…' for key 'orders.uk_user_request'
```

### 5.8 参数校验

| 请求 | 响应 |
|---|---|
| 不传 requestId | 400「缺少幂等键 requestId」 |
| `requestId: "a:b c"` | 400「幂等键格式不合法」 |

### 5.9 回归

`mvn test` 6 个测试全绿；前端 `npm run build` 通过。

## 六、面试问答

**Q：下单幂等怎么做的？**
两层。客户端每次购买意图带一个 requestId，服务端先用 Redis `SETNX` 占位，重复请求
直接返回上次的订单；`orders` 表还有 `(user_id, request_id)` 唯一索引，Redis 失效时由它兜底。

**Q：为什么不能只用 Redis？**
Redis 是外部依赖，可能挂、可能被 flush、key 可能过期。幂等的保证必须落在数据层，
否则只是"大部分时候有效"。

**Q：为什么不能只用唯一索引？**
能实现，但重复请求会完整跑一遍扣库存再回滚，而且要在事务外层捕获
`DuplicateKeyException` 才能返回正确结果。Redis 那层让第二次请求连事务都不开，
是性能和体验上的优化。

**Q：为什么 catch 必须在事务外层？**
`@Transactional` 方法内抛异常后事务被标记 `rollback-only`，在里面 catch 后继续查询，
方法返回时提交会抛 `UnexpectedRollbackException`。而且同一个类自我调用不走代理，
`@Transactional` 会失效，所以拆了一个 `OrderCreateGuard`。

**Q：requestId 谁生成？**
客户端。服务端生成的话每次都不一样，等于没有幂等。前端在进入结算页时用
`crypto.randomUUID()` 生成一次，整个页面生命周期不变；下单成功后才换新的。

**Q：用户下单失败后重试会被挡住吗？**
不会。失败时释放幂等键，同一个 requestId 可以立即重试。不释放的话用户会被自己的
失败请求挡住 30 秒，体验极差。

**Q：为什么是 409 而不是 400？**
409 Conflict 的语义是"请求与当前资源状态冲突"，重复提交正好是这个意思。
400 是请求本身不合法，这里是合法的，只是重复了。

**Q：30 秒的 TTL 怎么定的？**
要大于下单事务的最长耗时（否则第一个还没跑完锁就过期，两层退化成一层），
又要足够小（进程崩了用户不至于干等太久）。正常下单是 100ms 级，30 秒有 300 倍余量。

**Q：这个方案还有什么漏洞？**
① 删缓存/投递队列这类 afterCommit 动作失败时没有补偿（已记录，靠 TTL 和启动补灌兜底）；
② requestId 存在 24 小时，超期后同一 ID 理论上能再下一单，实际不会发生；
③ 没有对"同一用户短时间大量不同 requestId"做限流——那是防刷单的问题，不是幂等。
