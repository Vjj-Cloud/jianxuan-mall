# M4 代码讲解：订单

> 对应提交：`feat: 订单模块（M4）`
> 覆盖范围：两张表 → 实体 / Mapper → 原子扣库存 → 下单事务 → 状态机 → 5 个接口 → 并发实测
> 难度：**高**。这是整个项目唯一真正决定「能不能写进简历」的模块。

---

## 0. 这一模块到底在解决什么问题

商品和购物车都是「单人操作自己的数据」，怎么写都不会出大乱子。订单不一样，它会**同时动三张表**，而且在并发下必须保证「卖出去的数量 ≤ 库存」。

```
一次下单要同时完成 4 件事：
  1. 扣 stock、加 sales      （改 product）
  2. 写订单主表               （改 orders）
  3. 写订单明细（含价格快照）  （改 order_item）
  4. 从购物车删掉已下单商品    （改 cart_item）

这 4 步要么全成功，要么全失败。少做一步就是脏数据：
  扣了库存没建订单 → 钱没收到、货没了
  建了订单没扣库存 → 超卖
```

所以 M4 的核心不是「会写 CRUD」，而是三件事：**事务边界、防超卖、状态机**。

## 2. 建表：四个决定

### 2.1 表名必须是 `orders`

`ORDER` 是 SQL 保留字（`ORDER BY`）。表叫 `order` 的话，每条 SQL 都得写成：

```sql
SELECT * FROM `order` WHERE ...
```

少写一个反引号就是语法错误，而且是那种「本地能跑、换个环境就炸」的错。加个 `s` 一劳永逸。

Java 类名 `Order` 不受影响——类名和 SQL 关键字是两件事，只有表名要注意。

### 2.2 明细表存快照，这是刻意的冗余

```sql
CREATE TABLE `order_item` (
  `product_id`   BIGINT,
  `product_name` VARCHAR(100)  COMMENT '下单时快照',
  `cover`        VARCHAR(500)  COMMENT '下单时快照',
  `price`        DECIMAL(10,2) COMMENT '下单时快照',
  ...
)
```

按数据库范式，`product_name`、`price` 存在 `product` 表里，这里存一份是冗余。但**订单是历史凭证**。

场景：你 1 月份花 2999 买了台手机。3 月份商家把价格改成 2499、名字改了。如果你的订单是 `JOIN product` 查出来的，那么历史订单会显示 2499——你的购买记录被篡改了。

快照解决了这个问题：订单永远显示下单那一刻的事实。

> 面试话术：「这是**受控冗余**，用空间换历史正确性。同理，收货地址、下单时的用户名在订单里也应该存快照，因为用户后来可以改地址、注销账号。」

### 2.3 索引围绕查询建

```sql
KEY `idx_user_status` (`user_id`, `status`)        -- 用户查自己的订单，可按状态筛
KEY `idx_status_created` (`status`, `created_at`)  -- 后台按状态筛选 + 按时间排序
UNIQUE KEY `uk_order_no` (`order_no`)              -- 订单号唯一，兜住并发撞号
```

`idx_user_status` 的最左前缀是 `user_id`，所以「只查某用户全部订单」也能命中，不需要再建单独的 `user_id` 索引。

### 2.4 没有外键约束

`order_item.order_id` 没有 `FOREIGN KEY` 指向 `orders.id`。这是互联网项目的常规做法：

- 外键会在每次写入时检查父表、加额外的锁，高并发下是负担
- 分库分表后外键根本用不了

代价是一致性要靠应用层保证（我们的 `@Transactional` 就是在做这件事）。面试如果被问「为什么不用外键」，能说出这两点就够。

## 3. 下单的 7 步

`OrderService.create()` 是本模块的全部重点。按顺序拆开：

```
① 合并同商品        LinkedHashMap<productId, quantity>，重复传的行累加
② 按 productId 升序  统一加锁顺序，避免死锁
③ 查商品 + 预校验    一次性 selectBatchIds，校验存在/上架/库存，算总额，做快照
④ 原子扣库存         UPDATE ... WHERE stock >= ?，0 行即失败
⑤ 写订单主表         setOrderNo / totalAmount / status=PENDING
⑥ 写订单明细         orderId 由自增主键回填
⑦ 清购物车           只删本次下单的 productId
```

整个方法挂 `@Transactional(rollbackFor = Exception.class)`，①-⑦ 在同一事务里。

### 为什么是 `rollbackFor = Exception.class`

Spring 默认只对 `RuntimeException` 和 `Error` 回滚，**受检异常（`Exception` 的子类但不是 `RuntimeException`）默认不回滚**。

我们的 `BusinessException` 继承 `RuntimeException`，不加这个参数也会回滚。但显式写上是习惯——万一以后有人在这里调了一个抛受检异常的第三方方法，不至于踩「异常抛了但事务提交了」的坑。

> 另一个容易被忽略的点：`@Transactional` **只在外部调用时生效**。同类内部 `this.methodB()` 调用不走代理，事务注解形同虚设。这是 Spring AOP 的代理机制决定的。

## 4. 防超卖：整个项目最重要的一条 SQL

### 4.1 错误写法（先查再改）

```java
Product p = productMapper.selectById(id);     // 读到 stock = 1
if (p.getStock() >= qty) {                    // 判断：够
    productMapper.updateStock(id, p.getStock() - qty);   // 写入 0
}
```

两个用户同时买最后一件：

```
T1  A: selectById → stock = 1
T2  B: selectById → stock = 1        ← A 还没写，B 也读到 1
T3  A: update stock = 0（成功）
T4  B: update stock = 0（成功）      ← 同一件货卖了两次
```

问题不在判断逻辑，在于**判断和写入是两条 SQL，中间有窗口**。

### 4.2 正确写法（判断跟着写入走）

```sql
UPDATE product
   SET stock = stock - #{quantity},
       sales = sales + #{quantity}
 WHERE id      = #{productId}
   AND status  = 1
   AND deleted = 0
   AND stock  >= #{quantity}
```

关键在最后一行：**「库存够不够」这个判断被塞进了 `WHERE`**。

`UPDATE` 执行时 InnoDB 会对命中的行加行锁。后到的请求要么阻塞等锁，要么在拿到锁之后发现 `stock` 已经变小、不再满足 `stock >= qty`，于是**匹配 0 行**。

Java 侧：

```java
int rows = productMapper.deductStock(productId, quantity);
if (rows == 0) {
    throw new BusinessException(400, "库存不足，请刷新后重试");
}
```

`rows == 0` 就是「没抢到」，抛异常让整个订单事务回滚。

### 4.3 一句话总结

> **把判断交给数据库，在锁的保护下完成「判断 + 写入」。应用层只负责看影响行数。**

同一个思路在 M3 购物车（`quantity + delta <= stock`）已经用过一次，在 M4 变成「跨表 + 事务」的版本。

## 5. 为什么第 ② 步要按 productId 排序

多商品下单时，两个事务如果以不同顺序锁行，会死锁：

```
事务 A：下单 [商品1, 商品2]     先锁 1，再锁 2
事务 B：下单 [商品2, 商品1]     先锁 2，再锁 1

T1  A 锁住商品1
T2  B 锁住商品2
T3  A 想锁商品2 → 等 B 释放
T4  B 想锁商品1 → 等 A 释放
     ── 互相等待，死锁 ──
```

MySQL 会检测到死锁并回滚其中一个事务，用户看到的是「莫名其妙的 500」。

解法很简单：

```java
List<Long> productIds = quantityByProduct.keySet().stream().sorted().toList();
```

**所有事务都按同样的顺序加锁**，就永远不可能形成环。这是「破坏死锁四个必要条件之一（循环等待）」的标准做法。

> 这个点很容易被忽略，但面试官问「下单并发高的时候会出现什么问题」时，能答出死锁和排序破解，比只答超卖高一个层次。

## 6. 双层校验：预校验 + 原子扣减

代码里对库存做了两次检查，看起来冗余，其实是故意的：

| 层 | 位置 | 作用 |
|---|---|---|
| 预校验 | `selectBatchIds` 后在 Java 里 `if (stock < qty)` | **给出友好错误**（「XX 库存不足」） |
| 原子扣减 | `UPDATE ... WHERE stock >= ?` | **保证并发正确性** |

只有预校验不够：查完之后、扣之前，库存可能被别人买走。
只靠原子扣减也能跑，但错误消息只能笼统说「库存不足」，用户不知道该改哪件商品。

实测数据能看出两层都在工作——20 个并发请求抢 5 件库存：

```
成功 5 个 / 失败 15 个
失败原因分布：
  「纯棉基础圆领 T 恤」库存不足  × 10   ← 被预校验拦下（读到了已扣减的库存）
  库存不足，请刷新后重试         × 5    ← 被原子扣减拦下（预校验通过但扣减时已不够）
```

那 5 个「预校验以为够、扣减时不够」的，正是并发窗口里的请求——**如果没有第二层，这 5 件就超卖了**。

## 7. 状态机：`PENDING → SHIPPED → COMPLETED`

```
           取消（回补库存）
PENDING ──────────────────► CANCELLED
   │
   │ 管理员发货（M5）
   ▼
SHIPPED
   │
   │ 用户确认收货
   ▼
COMPLETED
```

规则：**只能沿着箭头走，不允许跳转**。已发货不能取消，已完成不能重复确认。

### 7.1 状态校验为什么用条件 UPDATE

直觉写法：

```java
if (!PENDING.equals(order.getStatus())) throw ...;
order.setStatus(CANCELLED);
orderMapper.updateById(order);
```

两个「取消」请求同时到达时会怎样？两步都读到 `PENDING`，都通过检查，都执行 update——**库存被回补两次**。

正确写法：

```java
int rows = orderMapper.update(null, new LambdaUpdateWrapper<Order>()
        .eq(Order::getId, orderId)
        .eq(Order::getStatus, PENDING)        // ← 条件也进 WHERE
        .set(Order::getStatus, CANCELLED)
        .set(Order::getUpdatedAt, LocalDateTime.now()));
if (rows == 0) throw new BusinessException(400, "订单状态已变更，请刷新后重试");
```

和扣库存完全同一个道理：**把「当前是不是 PENDING」写进 `WHERE`，让影响行数来裁决**。第一个请求拿到 1 行，第二个拿到 0 行直接被拒。

这是「乐观锁」思想最轻量的实现，不需要 version 字段。

### 7.2 取消时回补库存

```sql
UPDATE product
   SET stock = stock + #{quantity},
       sales = GREATEST(sales - #{quantity}, 0)
 WHERE id = #{productId}
```

`GREATEST(..., 0)` 是防御性写法：万一历史数据里 `sales` 小于要回退的数量（人工改过库、或数据迁移出错），不要让销量变成负数。

## 8. 订单号为什么不用自增主键

```java
"SO" + yyyyMMddHHmmss + 4 位随机数     // SO202611231250133098
```

三个理由：

1. **自增 id 会暴露业务量**。竞争对手下两单，看着 id 从 10001 跳到 15230，就知道你大概卖了多少。
2. **分库分表时无法保证全局唯一**。多库各自自增必然撞号。
3. **业务单号需要可读**。客服沟通时说「你 2026 年 11 月 23 日的订单」比说「你 id=12345 的订单」友好。

同一秒内的 4 位随机仍有约万分之一的碰撞概率，由 `uk_order_no` 唯一索引兜底——撞了就插入失败，不会产生两张同号订单。

## 9. 一个真实踩到的 bug：`createdAt` 是 null

第一版代码 `orderMapper.insert(order)` 之后直接 `return OrderVO.from(order, items)`，结果：

```
下单接口返回:  createdAt = null
订单列表查询:  createdAt = "2026-11-23T12:48:40"
```

原因：`orders.created_at` 有 `DEFAULT CURRENT_TIMESTAMP`，但**那是「INSERT 语句里没带这一列时，MySQL 自己填」**。MyBatis 插入后并不会把数据库生成的值读回 Java 对象，所以内存里的 `order.createdAt` 还是 null。

列表和详情是重新查库的，所以看着正常——**只有下单这一次返回缺字段**。这种「同一个字段，一个接口有一个接口没有」的 bug 特别难查，因为大多数人只会测列表页。

修法：插入前手动 `setCreatedAt` / `setUpdatedAt`。

顺带修了第二个问题：`LocalDateTime.now()` 带纳秒（`12:48:39.5840771`），而数据库 `DATETIME` 存到秒（`12:48:40`）——同一个字段两种精度。于是给 `OrderVO` 加了：

```java
@JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ss")
```

统一输出秒级 ISO 格式，前端 `new Date(str)` 各浏览器都能稳定解析。

## 11. 面试自测

**Q1：下单怎么防止超卖？**
`UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?`，判断和写入在同一条 SQL 里，由 InnoDB 行锁保证原子性。影响行数为 0 就抛异常回滚。

**Q2：为什么不先查库存再判断？**
查询和更新是两条 SQL，中间有网络往返窗口。两个请求可能同时读到 `stock=1`，都判断「够」，然后各自扣减 → 超卖。

**Q3：多个商品同时下单会有什么问题？**
死锁。两个事务以相反顺序锁行会互相等待。解法是按 productId 排序，让所有事务的加锁顺序一致。

**Q4：下单的事务范围应该多大？**
扣库存 + 建订单 + 建明细 + 清购物车必须在同一事务。订单号生成可以放事务内但要避免长事务（不要在事务里调用外部接口、发短信、发 MQ）。

**Q5：取消订单时重复点击会怎样？**
如果只做「查状态 + 改状态」两步，两个请求都读到 PENDING 都能通过。要用条件 UPDATE（`WHERE status='PENDING'`），影响 0 行即拒绝，库存只回补一次。

**Q6：为什么订单明细要存商品名和价格？**
订单是历史凭证。商品改价改名后，历史订单必须还原下单时的事实。这是受控冗余。

**Q7：`@Transactional` 什么情况下会失效？**
① 同类内部调用（不走代理）；② 方法不是 public；③ 异常被 catch 吞掉；④ 抛的是受检异常且没配 `rollbackFor`；⑤ 数据库引擎不支持事务（MyISAM）。

**Q8：为什么不用数据库外键？**
每次写入都要检查父表、加额外锁，高并发下是负担；分库分表后外键不可用。一致性靠应用层事务保证。

## 12. 已知的简化与下一步

| 简化 | 说明 |
|---|---|
| 没有支付 | 下单直接进入 `PENDING`（待发货），不涉及支付回调 |
| 没有超时取消 | 真实电商会有「30 分钟未支付自动取消」，需要定时任务 |
| 发货在 M5 | 现在测 `confirm` 是直接改库把状态设成 `SHIPPED` |
| 订单号碰撞不重试 | 概率约万分之一，撞了靠唯一索引报错，没有自动重试 |

**M5 要做的是**：管理端订单列表（按状态/订单号筛选）、发货接口（`PENDING → SHIPPED`）。接口不多，但要把「管理员只能发货、不能改价、不能删单」的边界守住。

## 13. 这一模块最值得记住的三句话

1. **判断要跟着写入走。** 超卖、重复取消、重复插入，全都是「先判断再写入」这个模式惹的祸。
2. **加锁顺序要一致。** 死锁不是靠重试解决的，是靠排序预防的。
3. **事务只覆盖必要的四步。** 事务越大，锁持有时间越长，吞吐越低。
