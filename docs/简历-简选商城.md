## 项目经历

### 简选商城 — 前后端分离电商系统 ｜ 个人项目 / 独立完成
**2026.09 – 2026.11**

技术栈：Spring Boot 3.5 · MyBatis-Plus 3.5 · MySQL 8 · Redis · JWT · BCrypt · Vue 3 + Vite

- 独立完成商品、购物车、订单、后台管理四个模块，共 **25** 个 RESTful 接口；按
  `controller / service / mapper / dto` 分层，对外只返回 VO 不直出实体；统一 `Result<T>` +
  全局异常处理，业务异常返回真实 HTTP 状态码（401/403/404/409），前端按状态码分流。
  鉴权用 JWT + BCrypt，登录态经 `ThreadLocal` 传递；拦截器坚持**先鉴权、后写入**——
  `preHandle` 抛异常时 Spring 不回调 `afterCompletion`，顺序反了会把身份残留在 Tomcat
  复用线程上造成用户串号。
- 下单流程用 `@Transactional` 保证「扣库存 / 建订单 / 建明细 / 清购物车」的原子性；库存扣减
  采用 `UPDATE ... WHERE stock >= ?` 单条 SQL 原子更新，受影响行数为 0 即抛异常回滚，
  从数据库层面杜绝超卖；购物车数量累加同样把校验放进 `WHERE`，避免「先查后改」的并发窗口。
- **下单幂等**：前端生成 `requestId` 随请求携带，服务端用 Redis `SETNX` 占位（值两态：
  `PROCESSING` → 订单 ID，TTL 30s / 24h），并以 `(user_id, request_id)` 唯一索引兜底。
  实测 10 线程并发同一 `requestId` 只落 1 单且全部返回 200，停掉 Redis 后重复提交仍返回
  同一订单（唯一索引兜底生效）。`DuplicateKeyException` 的捕获刻意放在事务外层——
  在事务内 catch 后继续查库，提交时必抛 `UnexpectedRollbackException`。
- **订单超时自动取消**：用 Redis ZSet 作延迟队列（member = 订单 id，score = 到期时间戳），
  Lua 脚本原子完成 `ZRANGEBYSCORE` + `ZREM`，保证多实例下同一任务只有一个消费者；
  `@Scheduled` 每秒轮询，应用启动时把库中 `PENDING` 订单补灌回队列（Redis 丢数据后仍能自愈），
  处理失败按 60 秒退避重试、3 次后转死信集合。实测超时阈值 12 秒时订单被准确取消，
  且「已发货不误取消」「手动取消不重复回补库存」「事务回滚不投递任务」三个边界均验证通过。
- **商品缓存**：Cache-Aside 模式，针对缓存穿透 / 击穿 / 雪崩分别用空值缓存、`SETNX` 互斥锁 +
  Lua token 释放、TTL 随机抖动；Redis 不可用时熔断降级（失败后 5 秒跳过缓存），
  把单次商品详情请求从「串行等待 3 次超时」的 **10.05 秒** 压到 **4.3 毫秒**。
  缓存删除放在事务提交后并延迟 1 秒补删——放在提交前，并发读会读到未提交的旧库存并回填，
  这个脏值在 TTL 内无人纠正。
- **压测与瓶颈定位**：发现同一秒内订单号随机后缀碰撞（240 单失败 2 单，与生日问题期望值
  0.94 吻合），改用雪花 ID 后 640 单零冲突；随后用 Python 多进程压测逐项排除连接池、
  SQL 控制台日志、压测客户端 GIL 三个伪瓶颈，确认写接口上限来自热点商品行锁——
  单商品 **145 QPS**，分散到 20 个商品后 **506 QPS**。
- **质量保障**：接受 3 轮外部代码评审共 **16 条**意见，逐条核实后修复——不是照单全收，
  而是区分「真 bug / 设计取舍 / 文档写错」三类分别处理。典型如金额精度按整条链路倒推
  （单价上限 × 数量上限 × 单笔 50 项，反推订单表字段精度），而非只看单表列宽；
  DTO 校验注解与 DDL 对齐，避免「用户输入越界」退化成 500。测试从 0 补到 **28 个用例**，
  其中幂等与缓存一致性用例刻意不加 `@Transactional`——加上之后 `afterCommit` 不执行、
  并发线程互不可见，会得到「全绿但什么都没验证」的假绿。
