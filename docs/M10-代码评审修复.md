## 1. 下单成功后 `await cartStore.load()` 可能造成第二笔订单

**原代码**（`Checkout.vue`）：

```js
await createOrder({ requestId: requestId.value, ... })
requestId.value = genRequestId()   // ← 先把幂等键换掉
await cartStore.load()             // ← 这一步可能抛异常
ElMessage.success('下单成功')
router.replace({ path: '/orders' })
```

**为什么是真 bug**：`createOrder` 成功意味着**订单已经在数据库里了**（钱货两清）。
但紧接着的 `cartStore.load()` 是一次普通 HTTP 请求，网络抖一下就会 reject。
`submit()` 只写了 `try/finally`、没有 `catch`，所以：

1. `finally` 把 `submitting` 复位，按钮又能点了；
2. 用户停留在结算页，看不到任何成功提示（提示在 `load()` 之后）；
3. `requestId` 在第 2 行已经被换成新的了。

于是用户以为「没提交成功」，再点一次 —— 后端收到的是一个**全新的幂等键**，
完全无法识别这是同一次购买意图，于是生成第二笔订单、再扣一次库存。

这是最坏的一类 bug：**用户以为自己失败了，其实已经买了两份**。

**修复**（三处，缺一不可）：

```js
ElMessage.success('下单成功')       // 1. 先把「成功」这个事实告诉用户
cartStore.load().catch(() => {})    // 2. 购物车刷新改成非阻塞，失败只是角标不准
await router.replace(...)           // 3. 跳转优先，且不再重置 requestId
```

为什么**不重置** `requestId`：万一跳转本身失败，用户又点了一次提交，
后端会把同一笔订单原样回放（幂等语义），而不是再下一单。
「重新进入结算页会重新生成」这件事由 `onMounted` 保证，不需要在这里手动换。

**这条能讲的面试点**：

- 幂等键的生成时机决定了它能覆盖多大的范围。放在「进页面」而不是「提交时」，
  是为了让「超时重试」和「手抖双击」共享同一个键。
- 幂等的最后一公里在前端：**成功响应之后不允许再有会失败的业务请求**。
  前后端都要防，前端防「用户重复点」，后端防「请求重复到」。
- 顺带修掉的两个小问题：`formRef.value.validate()` 校验失败时是 reject 而非返回 false，
  不接住会变成未处理的 Promise 拒绝；`submit` 也没有 `catch`，业务失败时控制台会多一条红字。

## 2. 取消订单时在事务提交前删缓存，旧库存可能被回填

**原代码**（`OrderService.cancelBySystem` / `cancel`）：

```java
for (OrderItem item : items) {
    productMapper.restoreStock(item.getProductId(), item.getQuantity());  // 事务内，未提交
}
evictProductCaches(productIds);   // ← 缓存先删了
return true;                       // 事务在这里才提交
```

原来的注释是这么辩解的：「删缓存放在提交前是安全的，万一事务回滚，库存根本没回补，
下次读回源拿到的仍然是正确值」。**这句话本身没错，但它只考虑了回滚，漏掉了并发**：

```
 T1（取消订单，事务中）        T2（读商品详情）
 ├─ UPDATE stock = stock + 1    │
 ├─ DEL cache:product:1         │
 │                        ├─ 缓存未命中 → 回源查库
 │                        │   读到的是「未提交」的旧库存
 │                        └─ 把旧库存写回缓存（TTL 30 分钟 + 抖动）
 └─ COMMIT
```

事务提交后库存已经是新值，但缓存里躺着旧值，而且**在 TTL 到期前没有任何动作会纠正它**。
用户看到「有货」，点下单却提示库存不足——正是 M8 里说的那种最难查的脏缓存。

**修复**：新增 `ProductCacheEvictor`，统一管「什么时候删」：

- `evictAfterCommit(ids)`：注册 `TransactionSynchronization`，只在**提交成功后**删；
  回滚时什么都不做（那时库存没变，缓存本来就没脏）；
- `evictNow(ids)`：立即删 + **1 秒后补偿再删一次**（延迟双删）；
- 所有删除都 `try/catch`：走到这里订单已经成功，不能因为 Redis 报错让接口返回 500。

**为什么还要延迟删**：`afterCommit` 之后立刻删，仍然有一个极窄的窗口——T2 在提交前发起
查询、在删除之后才写回缓存。这个偏差没法靠加锁彻底消除（那要把缓存读写塞进数据库事务里），
工业界的做法就是延迟双删，把那个慢半拍的读请求造成的回填也清掉。代价是一次多余的 DEL。

**一个容易写错的地方**：`afterCommit` 回调里**不能**再调 `evictAfterCommit`。
此时 `TransactionSynchronizationManager` 仍然是激活状态，新注册的同步器会跟着
`triggerAfterCompletion` 走，`afterCommit` 永远不会被回调——缓存就「看起来删了、其实没删」。
所以拆成两个方法，`create()` 的 `afterCommit` 里显式调 `evictNow`。

**面试点**：

- 「先删缓存还是先更库」的标准答案要加一个前提：**是否在事务里**。
  单条 UPDATE 自动提交时，先更库后删缓存就够了；在事务里，删除必须挪到提交之后。
- 「删除是幂等的所以什么时候删都安全」只对了一半：删除本身不写脏数据，
  但它打开了一个「读请求把旧值回填」的窗口，窗口的另一端是数据库的可见性。
- 延迟双删解决的是「概率」不是「确定性」，彻底方案是 binlog 订阅（Canal）异步失效。

## 3. 启动补灌不捕获 Redis 异常 / 任务取出后重入队失败会丢

**原代码**（`OrderTimeoutTask.run`）：

```java
@Override
public void run(ApplicationArguments args) {
    List<Order> pendingOrders = orderMapper.selectList(...);   // 有 PENDING 单就会进循环
    for (Order order : pendingOrders) {
        delayQueue.push(order.getId(), expireAt - now);        // ← Redis 挂了直接抛
    }
}
```

`ApplicationRunner` 抛异常 = **应用启动失败**。所以「库里有 PENDING 订单 + Redis 没启动」
时，后端起不来，与 README 里「Redis 没启动后端也能起来」的说法矛盾。
一个可选组件把主站拖死，是典型的可用性事故。

**修复**（`OrderTimeoutTask` + `OrderDelayQueue`）：

1. `run()` 全程 `try/catch`：数据库查不到、Redis push 失败都只记日志，不影响启动。
   单条 `createdAt == null` 的脏数据跳过而不是 NPE 中断整批。
2. `scan()` 里 `pollDue(Redis)` 单独包一层：Redis 故障时本轮跳过。
   用 `AtomicBoolean` 记录故障状态，**只在状态翻转时打日志**——
   否则 `@Scheduled(fixedDelay = 1000)` 会每秒打一条完整堆栈，把真正的故障信息淹掉。
3. 重新入队加重试计数：`pushForRetry(orderId, delay, 3)` 用 `HINCRBY` 累计，
   超过 3 次转 `order:delay:dead` 死信集合并打 ERROR；成功处理后 `clearRetry` 清计数。
4. 连「重新入队」都失败（Redis 正好挂了）时只记日志——这种情况没法优雅处理，
   靠**启动补灌**兜底。这也是为什么补灌不是可选优化，是这套设计的必要组成部分。

**面试点**：

- 任何一个「后台任务」都要回答两个问题：**失败了会不会拖垮主流程**、**失败的任务去哪了**。
  这里的答案分别是「不会（异常全吞 + 降级）」和「回队列，3 次后进死信」。
- 死信不是终点，它的价值是**把「无限重试的噪音」变成「一条待人工处理的记录」**。
- 定时任务里的异常必须自己吞：`@Scheduled` 抛异常不会重试、不会停止，只会每秒刷一条堆栈。

## 4. 关键新功能没有自动化测试覆盖

**原状**：`OrderServiceTest` 直接调 `orderService.create()`，**绕过了 `OrderCreateGuard`**，
而且连 `requestId` 都没设（插进去是 NULL）。而 `uk_user_request` 对 NULL 不做去重，
所以唯一索引在测试里从来没被触发过。结论：那 6 个绿灯证明不了幂等。

**修复**（新增 3 个测试类，直接从 6 个用例加到 18 个；第二轮又补了 6 个，见第 11/12 条，合计 24）：

| 测试类 | 覆盖 |
|---|---|
| `OrderIdempotencyTest`（3） | 同 requestId 顺序重复 → 回放同一笔；10 线程并发 → 只落 1 单；绕过 Guard 直接插 → 撞唯一索引 + 库存回滚 |
| `ProductCacheConsistencyTest`（2） | 下单后详情返回新库存；取消后详情返回回补后的库存 |
| `OrderTimeoutTaskTest`（7，纯 Mockito） | Redis 挂时 `scan`/`run` 不抛；取消失败重新入队；重试耗尽转死信；脏数据跳过 |

**两个关键的测试设计决定**：

1. **幂等测试不加 `@Transactional`**。幂等的前提是并发，并发的线程只能看到**已提交**的数据。
   放在测试事务里，所有线程都查不到对方的数据，会一起走到「插入」，测出来的结论和线上相反。
   所以这里用真实提交 + `@AfterEach` 手工清理。
2. **缓存一致性测试也不加 `@Transactional`**，理由更直接：失效被安排在 `afterCommit`，
   测试事务永远不提交，`afterCommit` 永远不执行 —— 断言会全绿但什么都没验证。
   「用 `@Transactional` 图省事」导致的假绿是最常见的一类测试陷阱。
3. 缓存断言看的是**「详情接口返回的库存」**而不是「key 是否存在」。
   key 是实现细节（改成延迟双删、改两次删除，断言就废了），库存才是契约。

## 5. 订单明细数量无上限，合并时整数溢出（比评审说的更严重）

**原代码**：`quantity` 只有 `@Min(1)`，`items` 只有 `@NotEmpty`。

评审说「存在整数溢出风险」，实际上它是**可以被真实利用的金额/库存漏洞**：

```java
quantityByProduct.merge(productId, quantity, Integer::sum);   // 两条 20 亿 → 负数
if (product.getStock() < quantity) throw ...                  // 负数 → 恒不成立，校验失效
UPDATE product SET stock = stock - #{quantity} ...            // stock - (-n) = 加库存
totalAmount = price × (-n)                                    // 负金额订单
```

也就是说：传两条各 20 亿的 quantity，可以「买」出一笔负金额订单，还顺手把库存加上去。

**修复**：`@Max(999)` + `@Size(max = 50)`，合并后最大值 49 950，远离溢出边界。
另外在 `OrderService.create` 里加了一层服务端自保（`quantity == null || <= 0` 直接拒绝），
因为**校验注解只在 Controller 那一层生效**，将来从定时任务/RPC 调进来是拦不住的。

## 6. 商品编辑接口没有 `@Valid`：一半是有意，一半是真缺口

原代码的注释写着「不加 `@Valid` 是为了支持部分更新」，这个理由成立：
`ProductSaveRequest` 上有 `@NotBlank` / `@NotNull`，加了 `@Valid` 就等于强迫前端每次全量提交。

但代价是**连纯格式校验也一起丢了**：`@Size(max = 100)`、`@DecimalMin`、`@Min(0)` 全部失效。
而 `ProductService.update` 只手工校验了「名称非空、售价 > 0、库存 >= 0」，
**长度**没校验 —— 传一个 300 字的商品名，会一路撞到 `varchar(100)` 报
`Data too long`，最后被兜底成 500「系统繁忙」。

**修复**：用 Bean Validation 的**校验分组**，让两件事同时成立。

```java
public interface Create {}
public interface Update {}

@NotBlank(groups = Create.class, message = "商品名称不能为空")
@Size(max = 100, groups = {Create.class, Update.class}, message = "商品名称最多 100 个字符")
private String name;
```

```java
// 新增：校验必填 + 格式
@Validated(ProductSaveRequest.Create.class) @RequestBody ProductSaveRequest req
// 编辑：只校验格式（长度、非负），不校验必填
@Validated(ProductSaveRequest.Update.class) @RequestBody ProductSaveRequest req
```

**必须知道的坑**：一旦用了具体分组，**没写 groups 的约束不会执行**。
Bean Validation 的组是「白名单」语义，不会隐式包含 `Default` 组。
所以每个约束都显式写了 groups —— 漏一个，那条校验就静默失效。

# 第二轮评审

第一轮的修复本身引入了两个新的边界（批量删除没做、测试清理只做了一半），
所以第二轮的重点不是「再找 bug」，而是「上一轮的修复在极端条件下是否还成立」。

## 11. 注册昵称没有长度校验：51 个字符返回 500

**原代码**：`RegisterRequest.nickname` 上没有任何约束，而 `user.nickname` 列是 `VARCHAR(50)`。

**为什么这是 bug 而不是「数据库报错很正常」**：用户输入越界属于**可预期的输入错误**，
应该返回 400 并告诉用户「昵称太长」。让它穿过校验层打到数据库，抛
`DataIntegrityViolationException`，最后被全局异常处理的兜底分支接住，用户看到的是
「系统繁忙，请稍后重试」——他会重试，然后永远失败。

**修复**：

```java
@Size(max = 50, message = "昵称最长 50 个字符")   // null 是放行的，正好符合「昵称可选」
private String nickname;
```

**这里的通用规则**：**DTO 的校验注解必须和 DDL 对齐**。
列的 `VARCHAR(n)`、`NOT NULL`、`UNIQUE` 都应该在 DTO 里有对应约束，
否则「数据库约束」就会变成「500 错误」。唯一的例外是唯一索引——
它必须保留，作为并发出错时的最后一道兜底（见 M9 的 `uk_user_request`）。

新增 `RegisterRequestValidationTest`（2 个用例）用纯 Bean Validation 验证：
51 个字符必须被拦下，不传 / 刚好 50 个字符必须放行。

## 12. Redis 故障时，删缓存可能拖慢「已经成功的订单」

**原代码**：`ProductCacheEvictor` 对订单里的每个商品 `forEach` 调一次 `evictDetail`，
而 `ProductCache.evict` 没有任何熔断检查。

**放大后的后果**：一笔订单最多 50 件商品。Redis 网络超时（本项目配 500 ms）时，
50 次串行 `DEL` = 25 秒。而这段代码跑在 `afterCommit` 里——**订单已经提交成功了**，
客户端却早就超时断开。用户看到「下单失败」，实际订单已经在库里，于是又下一单。

**修复**（`ProductCache.evictAll`）：

```java
if (cacheHealth.isOpen()) {          // 已知 Redis 挂了，不再白等一次超时
    return;
}
redisTemplate.delete(keys);          // DEL 支持多 key：一次往返删完
```

三个要点：

1. **批量命令**：`DEL key1 key2 ... key3` 是 Redis 原生支持的多 key 形式，
   服务端仍然是逐个删，但网络往返只有一次。N 次超时变成 1 次。
2. **熔断期直接返回**：这里没有重试入口，删失败就是失败，
   所以「跳过」和「尝试后失败」在结果上完全等价，区别只在响应时间——那当然选快的。
   代价是缓存脏到 TTL 过期，而 TTL 本来就是这条链路的兜底手段。
3. **熔断检查必须放在删除路径里**，不能只放在读路径。读路径有 `get()` 兜底，
   写/删路径如果没有，就会出现「读很快、下单很慢」这种极难排查的不对称现象。

新增 `ProductCacheEvictionTest`（4 个纯 Mockito 用例）：多 key 只发一条 `DEL`、
熔断期零 Redis 交互、删除失败吞异常但上报熔断、失效器把 50 个 id 一次交给缓存层。

## 13. 测试只在数据库里清理，Redis 里留下孤儿任务

**现象**：跑完测试后 `ZCARD order:delay` = 10，对应的订单 id 在 `orders` 表里全部不存在。

**原因**：`OrderIdempotencyTest` / `ProductCacheConsistencyTest` 为了测并发刻意不加
`@Transactional`，所以订单是**真提交**的，`afterCommit` 也**真执行**了——
延迟任务被投进 ZSet。而 `@AfterEach` 只删了数据库里的订单，Redis 那边没人管。

**为什么这不是业务 bug**：真实场景里订单不会凭空消失，队列里有历史任务是正常的。
问题出在测试「只清理了自己造的数据的一半」，跑几十次之后队列里全是噪音，
排查真实积压问题时会被误导。

**修复**：新增 `support/RedisTestCleanup`，在删库**之前**把订单 id 查出来，
一次性清掉三个 key：

| key | 什么时候会有 |
|---|---|
| `order:delay` | 下单成功后 `afterCommit` 投递 |
| `order:delay:retry` | 处理失败被 `HINCRBY` 记账 |
| `order:delay:dead` | 重试 3 次仍失败转死信 |

只清第一个是常见的半吊子做法——另外两个迟早也会变成垃圾。

## 14. 两处文档没跟着代码改

- README 写「17 个用例」，实际 18（本轮后 24）。
- `docs/M9` 的变更清单还写「成功后换新 requestId」，但第 1 条修复已经改成**不重置**，
  而且原因正好相反（重置会造出第二笔订单）。

**这类问题的危害**：文档和代码不一致时，读文档的人会以为代码是错的，
或者照着文档去「修正」代码，把已经修好的 bug 改回去。文档里的**
「为什么这么做」比「做了什么」更容易过期**，改代码时要顺手搜一遍关键词。

## 15. 下单成功弹了两次提示

结算页提交成功后弹 `ElMessage.success('下单成功')`，跳转到订单页时又根据
`?created=1` 弹一条「下单成功，等待商家发货」。两条消息叠在一起，
用户看到的是同一个事实被播报两遍。

**修复**：提示由**执行动作的地方**负责，删掉订单页那条和 `created` 查询参数。
顺带的好处是少了一个只用于弹提示的 URL 参数——这种参数一旦被分享出去，
别人打开链接也会莫名其妙看到「下单成功」。
