# 简选商城 · 后端开发指南

> 给 Jack 的施工图。前端已完成（Vue 3 + Element Plus，位于 `frontend/`），
> 接口以 `docs/api.md` 为准，本文回答"做什么、怎么做、为什么这么做"。

---

## 1. 项目定位与 MVP 边界

**一句话**：一个前后端分离的单体商城，用户端浏览/加购/下单，管理后台维护商品和处理发货。

**范围内（必须做）**

- 用户注册、登录（JWT 鉴权）
- 商品分类、商品列表（搜索/筛选/排序/分页）、商品详情
- 购物车增删改查
- 下单（核心：库存扣减防超卖）、订单列表、取消、确认收货
- 管理后台：商品 CRUD + 上下架、订单查看 + 发货

**范围外（明确不做，面试时主动说）**

- 支付对接（订单直接进入"待发货"）
- 优惠券、秒杀、评价、退款
- 微服务拆分、Redis 缓存（第一版不做，见文末"进阶预留"）

> 面试价值不在功能多，而在每个点能讲透。MVP 做扎实，再谈扩展。

## 2. 角色与用例

| 角色 | 能做什么 |
|---|---|
| 游客 | 浏览分类/商品列表/详情、注册、登录 |
| 普通用户 USER | 游客能力 + 购物车 + 下单 + 查看/取消自己的订单 + 确认收货 |
| 管理员 ADMIN | 后台登录 + 商品管理（增删改查/上下架）+ 订单管理（查看/发货） |

同一套登录接口，靠 `user.role` 区分；管理端接口统一在 `/api/admin/**` 下，拦截器校验角色。

## 3. 业务流程

### 3.1 注册 / 登录

1. 注册：校验用户名唯一 → 密码 **BCrypt** 加密后入库 → 直接签发 token 返回（注册即登录）
2. 登录：按用户名查用户 → `BCrypt.matches(明文, 哈希)` 校验 → 签发 JWT
3. JWT 载荷放 `userId`、`role`，有效期 7 天
4. 前端所有请求带 `Authorization: Bearer <token>`；后端拦截器解析，失败返回 401
5. 管理端接口在拦截器里二次校验 `role == ADMIN`，失败返回 403

**注意**：密码泄漏风险不是"能登录就行"，MD5 可撞库、无盐；BCrypt 自带盐且慢哈希，这是面试必问。

### 3.2 浏览商品（公开接口）

- 列表只查 `status = 1`（上架）的商品
- 支持 `keyword`（名称/副标题模糊）、`categoryId`、`sort`（priceAsc / priceDesc / salesDesc）、`page` + `size`
- 详情查已下架商品返回 404

### 3.3 加入购物车

1. 校验商品存在且上架、库存 > 0
2. 同一用户同一商品已存在 → 数量累加（不超过库存），否则新增一行
3. 数据库用 `UNIQUE KEY (user_id, product_id)` 兜底，防止并发下插入重复行（捕获唯一键冲突后转为累加）

### 3.4 下单（全项目核心，重点准备）

请求体：`items: [{productId, quantity}]` + 收货人信息。流程：

```
开启事务
  ├─ 1. 对每个 item 做原子扣库存：
  │     UPDATE product
  │        SET stock = stock - #{qty}, sales = sales + #{qty}
  │      WHERE id = #{productId}
  │        AND status = 1
  │        AND stock >= #{qty}
  │     影响行数 = 0 → 抛业务异常（库存不足/已下架），整个事务回滚
  ├─ 2. 生成订单号（雪花 ID 或 时间戳+用户尾号+随机数），插入 orders
  ├─ 3. 批量插入 order_item（商品名、价格、封面做快照）
  ├─ 4. 删除购物车中已下单的商品
提交事务
```

**为什么用 `UPDATE ... WHERE stock >= qty` 而不是"先查库存再判断再更新"？**
先查后改在并发下会超卖（两个请求都查到 1 件库存）。条件更新由 InnoDB 行锁保证原子性，影响行数为 0 即失败。这是本项目最重要的一个面试点，务必能画出来讲。

**为什么 order_item 要存商品名和价格快照？**
订单是历史凭证。商品改价改名后，历史订单必须保持下单时的样子。表结构冗余是刻意的。

**金额一律 `DECIMAL(10,2)`，不用 double/float**（浮点精度问题）。

### 3.5 订单状态机

```
           取消(仅待发货可取消，回补库存)
PENDING ──────────────────────────────► CANCELLED
   │
   │ 管理员发货
   ▼
SHIPPED
   │
   │ 用户确认收货
   ▼
COMPLETED
```

- 所有状态变更接口都必须先校验**当前状态**，不允许跳转（如已发货不能取消）
- 取消订单要回补 `stock`、回退 `sales`，与下单逻辑对称

### 3.6 管理后台

- 商品管理：分页列表（含下架商品）、新增、编辑、删除、上下架
- 订单管理：分页 + 按状态/订单号筛选、发货（PENDING → SHIPPED）
- 删除商品建议**逻辑删除**（`deleted` 字段）或至少先判断无进行中订单；MVP 允许物理删除，但要能说出风险

## 4. 数据库设计

### 4.1 关系

```
user 1 ── n cart_item n ── 1 product n ── 1 category
user 1 ── n orders    1 ── n order_item n ── 1 product
```

### 4.2 建表 DDL（MySQL 8.0，utf8mb4）

```sql
CREATE TABLE `user` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `username`   VARCHAR(50)  NOT NULL COMMENT '登录名',
  `password`   VARCHAR(100) NOT NULL COMMENT 'BCrypt 哈希',
  `nickname`   VARCHAR(50)  NOT NULL DEFAULT '' COMMENT '昵称',
  `role`       VARCHAR(20)  NOT NULL DEFAULT 'USER' COMMENT 'USER / ADMIN',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户';

CREATE TABLE `category` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `name`       VARCHAR(50) NOT NULL,
  `sort`       INT NOT NULL DEFAULT 0 COMMENT '排序值',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品分类';

CREATE TABLE `product` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `category_id`    BIGINT UNSIGNED NOT NULL,
  `name`           VARCHAR(100) NOT NULL,
  `subtitle`       VARCHAR(200) NOT NULL DEFAULT '',
  `price`          DECIMAL(10,2) NOT NULL COMMENT '售价（元）',
  `original_price` DECIMAL(10,2) NOT NULL COMMENT '划线价（元）',
  `stock`          INT NOT NULL DEFAULT 0 COMMENT '库存',
  `sales`          INT NOT NULL DEFAULT 0 COMMENT '销量',
  `status`         TINYINT NOT NULL DEFAULT 1 COMMENT '1 上架 / 0 下架',
  `cover`          VARCHAR(500) NOT NULL DEFAULT '' COMMENT '封面图 URL',
  `description`    TEXT NULL COMMENT '详情',
  `created_at`     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_status_category` (`status`, `category_id`),
  KEY `idx_sales` (`sales`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品';

CREATE TABLE `cart_item` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`    BIGINT UNSIGNED NOT NULL,
  `product_id` BIGINT UNSIGNED NOT NULL,
  `quantity`   INT NOT NULL DEFAULT 1,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_product` (`user_id`, `product_id`),
  KEY `idx_user` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='购物车条目';

CREATE TABLE `orders` (
  `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`         VARCHAR(32) NOT NULL COMMENT '业务订单号',
  `user_id`          BIGINT UNSIGNED NOT NULL,
  `total_amount`     DECIMAL(10,2) NOT NULL,
  `status`           VARCHAR(20) NOT NULL DEFAULT 'PENDING'
                     COMMENT 'PENDING/SHIPPED/COMPLETED/CANCELLED',
  `receiver_name`    VARCHAR(50)  NOT NULL DEFAULT '',
  `receiver_phone`   VARCHAR(20)  NOT NULL DEFAULT '',
  `receiver_address` VARCHAR(255) NOT NULL DEFAULT '',
  `shipped_at`       DATETIME NULL,
  `created_at`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_status` (`user_id`, `status`),
  KEY `idx_status_created` (`status`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单';

CREATE TABLE `order_item` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_id`     BIGINT UNSIGNED NOT NULL,
  `product_id`   BIGINT UNSIGNED NOT NULL,
  `product_name` VARCHAR(100) NOT NULL COMMENT '下单时快照',
  `cover`        VARCHAR(500) NOT NULL DEFAULT '' COMMENT '下单时快照',
  `price`        DECIMAL(10,2) NOT NULL COMMENT '下单时单价快照',
  `quantity`     INT NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_order` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单明细（含商品快照）';
```

### 4.3 设计决策速记（面试可讲）

- **金额 DECIMAL、整数库存**：避免浮点误差；库存扣减用 SQL 原子操作
- **订单明细存快照**：历史订单不受商品变价改名影响
- **唯一索引承担并发约束**：用户名、订单号、用户+商品（购物车）
- **索引围绕查询建**：后台按状态筛选订单 → `(status, created_at)`；用户查自己订单 → `(user_id, status)`
- **不用外键约束**（互联网常规做法）：应用层保证一致性，减少锁开销；但要能说出代价
- **`created_at/updated_at` 数据库层自动维护**：减少应用代码

## 5. 接口契约

详见 [api.md](./api.md)。前端已按该契约开发，**字段名、枚举值、返回结构不要改**；
若确需调整，先改契约文档并同步前端，再改代码。

统一返回体：

```json
{ "code": 200, "message": "ok", "data": {} }
```

`code`：200 成功 / 400 业务或参数错误 / 401 未登录 / 403 无权限 / 404 不存在 / 500 系统异常。
除 401/403 用对应 HTTP 状态码外，业务错误统一 HTTP 200 + 业务 code。

## 6. 技术方案

| 事项 | 方案 |
|---|---|
| 框架 | Spring Boot 3.x + JDK 17 |
| 持久层 | MyBatis-Plus（自带分页插件、自动填充） |
| 数据库 | MySQL 8 |
| 密码 | `spring-security-crypto` 中的 `BCryptPasswordEncoder`（不必引入整套 Security） |
| 鉴权 | JWT（jjwt 0.12.x）+ HandlerInterceptor |
| 参数校验 | `jakarta.validation`（@Valid + 全局异常处理） |
| 接口文档 | Knife4j / springdoc-openapi |
| 统一返回 | `Result<T>` 泛型 + `@RestControllerAdvice` 全局异常 |
| 跨域 | 开发期 Vite 已配代理则无需 CORS；直连时配 CorsFilter |
| 金额 | Java 用 `BigDecimal` |

**前端切到真实后端两步**：
1. `frontend/src/main.js` 删除或注释 `import './mock'`
2. `frontend/vite.config.js` 打开 `server.proxy` 配置（指向 8080）

## 7. 开发顺序（按里程碑推进，每步可验收）

- **M0 工程骨架**：建项目、连库、`Result`、全局异常、分页插件、Knife4j，跑通一个 `GET /api/ping`
- **M1 用户模块**：注册/登录/me + JWT 拦截器 + 统一 401/403，用 Postman 验收
- **M2 分类与商品**：公开列表（分页/搜索/排序）+ 详情，塞 16 条种子数据
- **M3 购物车**：增删改查 + 唯一索引并发处理
- **M4 订单（核心）**：下单事务 + 防超卖 + 状态机（取消/确认收货）；用并发脚本验证不超卖
- **M5 管理后台**：商品 CRUD/上下架 + 订单查询/发货 + 角色拦截
- **M6 联调与收尾**：前端关闭 mock 联调；JMeter 压测下单接口；README（架构图、接口文档、压测数据）

> 建议每天一个里程碑，M4 单独留整天。先跑通单体，暂时不要拆微服务。

## 8. 高频面试追问清单（对着自测）

**认证**
- 为什么用 BCrypt 而不是 MD5/SHA？→ 自带随机盐、慢哈希、可调 cost
- JWT 无状态的好处与代价？→ 免查库、水平扩展；代价是无法主动失效、续期要另做方案
- token 放哪？→ 前端 localStorage（本项目）；能说出 XSS 风险与 httpOnly Cookie 的取舍

**商品与分页**
- 模糊搜索 `like '%kw%'` 用得上索引吗？→ 不能，数据量大要上 ES/倒排；面试主动指出局限
- 深分页问题？→ 大 offset 慢，可讲游标分页思路

**购物车**
- 唯一索引冲突怎么处理？→ 捕获 DuplicateKeyException 转累加，或 `ON DUPLICATE KEY UPDATE`

**订单（重点）**
- 怎么防超卖？→ 条件更新 `WHERE stock >= qty`，影响行数判断；对比先查后改的问题
- 事务范围？→ 扣库存 + 建单 + 建明细 + 清购物车在同一事务；订单号生成放事务内但要避免长事务
- 重复提交怎么办？→ 前端按钮 loading + 后端幂等（token/请求指纹），能说出方案即可
- 取消后库存怎么回补？→ 与下单对称的 UPDATE，注意状态校验防重复回补
- 订单号怎么生成？→ 雪花算法或"时间戳+用户+随机"，唯一索引兜底

**表设计**
- 为什么订单明细要冗余商品信息？→ 快照，历史凭证
- 金额为什么不用 double？→ 浮点精度
