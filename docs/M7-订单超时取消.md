# M7 · 订单超时未支付自动取消

> **状态：已实现并实测通过（2026-11-23）。**
> 本文最初是设计任务卡，现在保留下来作为「设计决策记录」——每一步的验收标准仍然有效，可以用来复查。
>
> 实测结果（超时设为 12 秒）：
> - 下单后 ZSet 出现任务，score 比当前时间晚 11.7 秒
> - 到期后订单自动变 `CANCELLED`，库存 300→299→300、销量同步回补，队列自动清空
> - 下单后立刻 `PUT /api/admin/orders/{id}/ship` 发货，超时任务跑到时状态保持 `SHIPPED`，库存不回补
> - 用户手动取消后再等超时，库存只回补一次（45→43→45，没有变成 47）
> - 原有 6 个测试仍全绿，无回归
>
> 实际落地的文件：`service/OrderDelayQueue.java`、`task/OrderTimeoutTask.java`、
> `OrderService.cancelBySystem()`、`OrderService.create()` 末尾的 afterCommit 投递。

## 一、目标与验收标准

**业务目标**：订单创建后 30 分钟仍未支付，自动关闭并回补库存。用户不再需要手动取消。

**验收标准**（写完逐条打勾）：

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | 下单后 Redis 里出现对应的延迟任务 | `ZCARD order:delay` 增加 1 |
| 2 | 超时后订单自动变 `CANCELLED` | 把超时时间调成 10 秒，下单后等 15 秒查库 |
| 3 | 库存和销量被正确回补 | 下单前后对比 `product.stock` / `sales` |
| 4 | 已发货的订单不会被误取消 | 下单后立刻手工改成 `SHIPPED`，等超时，状态不变 |
| 5 | 同一个订单不会被取消两次 | 观察库存没有被回补两遍 |
| 6 | 重启后端后，未到期的任务还在 | 下单 → 停后端 → 起后端 → 任务仍执行 |

## 二、整体流程

```
用户下单
   │
   ├─ ① MySQL 事务：写 orders、order_item，扣库存加销量
   │
   └─ ② 事务提交后（afterCommit）：ZADD order:delay <orderId> <到期时间戳>
                                          │
                                          ▼
                          调度线程每秒 ZRANGEBYSCORE 取到期任务
                                          │
                                          ▼
                              条件 UPDATE status: PENDING → CANCELLED
                                          │
                              ┌───────────┴───────────┐
                          影响 1 行                 影响 0 行
                              │                        │
                        回补库存、销量            状态已变（已支付/已发货）
                                                        │
                                                    静默跳过
```

## 三、为什么是 ZSet（这是面试的第一个问题）

| 方案 | 能不能用 | 问题在哪 |
|---|---|---|
| **ZSet（选它）** | ✅ | score 存到期时间戳，`ZRANGEBYSCORE 0 now` 精确取出「已经到期」的任务，天然按时间排序 |
| List | ❌ | 只能先进先出，没法按时间取；要延迟就得每个任务一个 List，key 数量爆炸 |
| Redis 键过期通知 | ❌ | 通知是**最多一次**投递，订阅端断线就永久丢；且过期删除是惰性+定期，不保证准时 |
| 定时扫表 | 可兜底 | 延迟精度受扫描间隔限制，订单量大时全表扫不动。**但适合做兜底补偿**，见第九节 |

**一句话答法**：ZSet 的 score 是到期时间戳，取任务就是一次范围查询，不需要为每个任务维护独立结构；而且 `ZRANGEBYSCORE` 能一次批量取，天然支持横向扩容时多个消费者分片。

## 四、数据结构设计

| Key | 类型 | Member | Score | 说明 |
|---|---|---|---|---|
| `order:delay` | ZSet | `orderId` | 到期时间戳（**毫秒**） | 待执行的延迟任务 |

- **Score 用毫秒不是秒**：秒级精度在测试时（设 10 秒超时）容易因为边界抖动出现「早 1 秒取不到、晚 1 秒才执行」的错觉，排查起来浪费时间。
- **Member 只放 orderId**：不放 JSON。任务内容越简单，重试和去重越容易——订单详情从库里查，库里才是真相来源。

### 第 2 步：`config/RedisConfig.java`（新建）

需要做的事：
1. 提供 `StringRedisTemplate`（其实自动配置已经有了，可以先不写这个类，直接用注入的 `StringRedisTemplate`）
2. 提供 `DefaultRedisScript<List>` 的 Bean，把下面这段 Lua 装载进去

**建议先用自动配置的 `StringRedisTemplate`，跑通再考虑自定义序列化。** 延迟队列的 key 和 member 都是字符串，用 `StringRedisTemplate` 最省事，还能直接在 `redis-cli` 里肉眼检查——这一点在调试时价值极大。

**Lua 脚本**（原子地「取出并删除」到期任务）：

```lua
local jobs = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #jobs == 0 then
  return {}
end
redis.call('ZREM', KEYS[1], unpack(jobs))
return jobs
```

逐行解释：
- `ZRANGEBYSCORE key 0 now LIMIT 0 N`：取 score 在 `[0, now]` 之间的前 N 个成员，也就是「已经到期的任务」
- 如果是空就返回空表，避免空跑 `ZREM`
- `ZREM` 和上面的查询在**同一个脚本**里执行。Redis 执行 Lua 是单线程原子的，所以这中间不可能插进第二个消费者——这是「不重复消费」的全部秘密

> 为什么必须用 Lua，不能分两次调用？如果先 `ZRANGEBYSCORE` 再 `ZREM`，两个调度线程可能同时读到同一批 orderId，同一个订单被取消两次（库存回补两遍）。虽然你现有的条件 UPDATE 能挡住（第二次影响 0 行），但那是「靠下游兜底」，不是设计正确。

**验收**：在 `redis-cli` 里手动 `ZADD order:delay 1 999`，跑一次脚本能取回 `999` 且 ZSet 变空。

### 第 3 步：`service/OrderDelayQueue.java`（新建）

两个方法：

```java
/** 把订单放进延迟队列，到期时间 = 现在 + timeoutMinutes */
public void push(Long orderId, long delayMillis)

/** 取一批已到期的订单 id，没有则返回空集合（不返回 null） */
public List<Long> pollDue(int batchSize)
```

要点：
- `push` 用 `ZADD`，score 是 `System.currentTimeMillis() + delayMillis`
- `pollDue` 用第 2 步的 Lua 脚本，`ARGV[1] = System.currentTimeMillis()`，`ARGV[2] = batchSize`
- 返回 `List<Long>`，空集合用 `Collections.emptyList()`，别返回 `null`——调用方少一个判空分支

**验收**：写一个临时测试或临时接口，调 `push(1L, 5000)`，`redis-cli ZRANGE order:delay 0 -1 WITHSCORES` 能看到 id 和 5 秒后的时间戳。

### 第 4 步：`OrderService.create()` 末尾挂上 push（⚠️ 最关键的一步）

**这里有个必须避开的坑：不能在 `@Transactional` 方法体里直接 push。**

因为 `create()` 是事务方法，push 在事务提交**之前**就执行了。如果后面任何一步抛异常导致回滚，订单没进库，但 Redis 里的延迟任务已经存在 → 到点去取消一个不存在的订单。

正确做法是**事务提交成功之后**再 push。两种写法，任选：

**写法 A：`TransactionSynchronizationManager`**

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            orderDelayQueue.push(orderId, ...);
        }
    });
```

**写法 B：`@TransactionalEventListener(phase = AFTER_COMMIT)`**

在 `OrderDelayQueue` 里加一个监听方法，`create()` 里用 `ApplicationEventPublisher` 发一个 `OrderCreatedEvent`。

> 写法 B 更解耦，也是生产里更常见的形态；写法 A 更直观、不引入事件类。**建议先用 A 跑通，理解了再考虑要不要重构成 B**——两件事一起做容易分不清是哪一步出的错。

还有一个细节：`create()` 现在返回 `OrderVO`，`orderId` 从返回值里取（`OrderVO.getId()`），不用额外查库。

**验收**：下单一笔，`ZCARD order:delay` 从 0 变 1；再故意让下单失败（比如数量超库存），`ZCARD` 不应该增加。

### 第 5 步：`service/OrderService.java` 加 `cancelBySystem(Long orderId)`

**为什么不直接复用 `cancel(userId, orderId)`？**

`cancel` 的第一个参数是 userId，且查询条件带 `eq(Order::getUserId, userId)` —— 系统任务没有"当前用户"。硬塞一个 userId 进去要么查不到，要么得先把订单查出来再传，绕。

新方法要做的事（**几乎全是复制 `cancel` 的逻辑，但去掉用户维度**）：

1. 按 id 查订单（**不带 userId**）
2. 查不到 → 记 warn 日志后返回（订单可能被物理删了）
3. 条件 UPDATE：`eq(id).eq(status, PENDING).set(status, CANCELLED)`
4. **`rows == 0` 时不要抛异常**，这是正常情况（用户已支付/已发货/已手动取消），记 info 日志后 `return`
5. 回补库存：`loadItems` + `restoreStock`（跟 `cancel` 完全一样）

> 第 4 点是和 `cancel` 最大的区别。`cancel` 面向用户，状态不对就该报错让他刷新；`cancelBySystem` 面向后台，状态变了说明「本来就不该取消」，是预期内的正常分支。**区分「业务异常」和「正常的不同结果」，是这段代码里最能体现工程判断的地方。**

**验收**：单元测试或临时接口调 `cancelBySystem`，传一个 `CANCELLED` 状态的订单 id，不抛异常、库存不变。

### 第 6 步：`task/OrderTimeoutTask.java`（新建）

```java
@Component
@RequiredArgsConstructor
public class OrderTimeoutTask {

    @Scheduled(fixedDelay = 1000)
    public void scan() {
        // pollDue(100) → 逐个调 cancelBySystem → 单个失败不影响整批
    }
}
```

要点：
- `@Scheduled(fixedDelay = 1000)`：**`fixedDelay` 不是 `fixedRate`**。`fixedDelay` 是「上一次执行结束后再等 1 秒」，任务慢的时候不会堆积；`fixedRate` 是「每 1 秒触发一次」，任务超过 1 秒就会并发堆积
- **循环里必须 try-catch**：一个订单处理失败不能让后面 99 个都不执行
- 批大小 100 是经验值，太大单次事务时间长，太小空转频繁

**别忘了在主类加 `@EnableScheduling`**，否则 `@Scheduled` 静默不生效——这是最常见的「代码明明写了就是不跑」。

**验收**：下单后观察日志，超时时间调到 10 秒，能看到任务触发并打出「取消订单 xxx」。

### 第 7 步：失败重试 + 重试上限 + 死信（已实现）

流程是「Lua 取出来 → 处理」。如果 `cancelBySystem` 抛了非业务异常（比如数据库连接抖了一下），这个任务已经被 `ZREM` 删掉了，**订单就永远不会被取消**。所以失败必须塞回去：

```java
catch (Exception e) {
    requeue(orderId, e);        // pushForRetry：HINCRBY 记次数，3 次后转死信
}
```

只塞回去还不够，会「无限重试」：一条坏数据每分钟重试一次、每次一条 ERROR，既清不掉也看不见。
现在做的是三层：

| 机制 | 实现 | 为什么 |
|---|---|---|
| 重新入队 | `pushForRetry(orderId, 60s, 3)` | 任务已出队，不塞回就永久丢失 |
| 重试上限 | `HINCRBY order:delay:retry {orderId}`，超过 3 次不再重试 | 连续 3 次失败基本是数据/代码问题，重试只是刷日志 |
| 死信集合 | `ZADD order:delay:dead` + ERROR 日志 | 把「无限重试的噪音」变成「一条待人工处理的记录」 |
| 计数清理 | 处理成功后 `clearRetry` | 不清的话这个订单会提前消耗下一次的重试配额 |
| 兜底 | 启动补灌 | 连「重新入队」都失败（Redis 正好挂了）时，只能靠重启补灌 |

**更要紧的一条**：`run()`（启动补灌）里所有 Redis 调用都必须吞异常。
它实现的是 `ApplicationRunner`，抛出即「应用启动失败」——库里有 PENDING 订单 + Redis 没启动，
后端起不来。一个可选组件把主站拖死，是典型的可用性事故。同理 `scan()` 里的 `pollDue`
也要单独兜住，否则 `@Scheduled` 会每秒打一条完整堆栈把日志刷爆（用 `AtomicBoolean` 只在
状态翻转时打一条 WARN）。

## 六、测试时的超时时间怎么调

`order.timeout-minutes` 是分钟级，测试时不可能等 30 分钟。两个办法：

1. **把配置改成小数**：`timeout-minutes: 0.2`（12 秒）。Spring 的 `@Value` 转 `Double` 没问题，注意类里要用 `double` 而不是 `long`
2. **直接用启动参数覆盖**：`--order.timeout-minutes=0.2`，不用改文件

推荐第 2 种，不动配置文件。

## 七、历史 PENDING 订单怎么办

你的库里现在有 5 笔历史订单，它们从没进过 ZSet，永远不会被自动取消。

这暴露了一个真实问题：**队列和数据库是两套状态，队列丢了数据就补不回来。** 两个应对：

| 做法 | 说明 |
|---|---|
| **启动时补灌**（简单） | 应用启动后查一遍 `status = PENDING` 的订单，`ZADD` 回队列。注意 `ZADD` 天然幂等，重复灌不会产生重复任务 |
| **定时扫表兜底**（更稳） | 每小时跑一次「`PENDING` 且 `created_at < now - 30min`」的订单，逐个 `cancelBySystem`。正好用上你表里的 `idx_status_created` 索引 |

> 面试如果问「Redis 挂了任务丢了怎么办」，答「有定时扫表兜底，队列只是把响应时间从 1 小时缩短到 1 秒，正确性不依赖它」——这个答案比「我会开 AOF」高一个层次，因为它承认了「任何单点都不可信，正确性要靠幂等 + 兜底」。

## 八、顺手该开的一个配置

你现在这台机器的 Redis 是 `appendonly no`（只靠 RDB 快照）。这意味着 Redis 重启后，最后一次快照之后的延迟任务全部丢失。

开发环境无所谓，但既然要写进简历，建议把 `D:\redis\redis.windows.conf` 里的 `appendonly no` 改成 `yes`，重启 Redis。AOF 每秒刷盘，最多丢 1 秒的数据，这是「消息不丢」的实际落地。
