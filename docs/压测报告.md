# 压测报告

> 环境：Windows 11 / JDK 17 / Spring Boot 3.5.16 / MySQL 8.0.29 / 单机，客户端与服务端在同一台机器
> 脚本：`scripts/benchmark.py`（纯标准库实现，可复现）
> 日期：2026-11-23

---

## 先说结论

| 结论 | 数据 |
|---|---|
| 读接口（商品列表） | 约 **2400 req/s**，8 进程客户端已到采样上限，服务端仍未饱和 |
| 写接口（下单） | 单商品 **145 req/s**，分散到 20 个商品后 **506 req/s** |
| 单请求基线延迟 | 读 1.6ms / 下单 7.6ms |
| 压测中发现并修复的 bug | **订单号唯一键冲突**，240 单挂 2 单 |
| 压测中排除的伪瓶颈 | 连接池大小、SQL 控制台日志、Python GIL |
| 压测中确认的真瓶颈 | **热点商品行锁** |

**这些数字不能当作线上容量。** 客户端和服务端抢同一台机器的 CPU，网络延迟接近 0，真实线上 QPS 通常远低于此。它的价值在于**横向对比**：改动前后同一条件下谁更快，以及**定位瓶颈在哪**。

## 1. 压测发现的真实 bug：订单号会撞

第一轮 32 并发、共 240 次下单，**失败了 2 个**，返回 `500 系统繁忙`。

查库：

```sql
SELECT LEFT(order_no,16) AS sec, COUNT(*) c FROM orders GROUP BY LEFT(order_no,16) HAVING c>1;
```

```
SO20261123131039   138 单
SO20261123131038    53 单
SO20261123131040    47 单
```

同一秒内进了 138 单。而当时的订单号是：

```
SO + yyyyMMddHHmmss（14 位）+ 4 位随机数
```

随机空间只有 10000。按生日问题算，138 单的期望碰撞次数：

```
C(138,2) / 10000 ≈ 9438 / 10000 ≈ 0.94
```

和实测失败的 2 单完全吻合。这不是环境抖动，是**设计缺陷**——QPS 越高越容易撞，而且报错是 `DuplicateKeyException` 被兜底成「系统繁忙」，从日志表面看不出根因。

### 修复：换成雪花 ID

```java
private String generateOrderNo() {
    return "SO" + IdWorker.getIdStr();   // MyBatis-Plus 内置
}
```

雪花 ID = 41 位时间戳 + 10 位机器号 + 12 位序列，同一毫秒可出 4096 个，天然全局唯一且有序。

修复后复测：240 单全部成功，订单号 248 个不重复（含之前的）。

**代价**：订单号不再包含可读日期（`SO2124732581566275586`）。业务上无影响——列表里有 `createdAt`，客服查询是等值匹配。唯一索引 `uk_order_no` 保留作兜底。

> 这个 bug 只有在压测（或真实秒杀）时才会暴露。功能测试一次一单，永远不会撞。

## 2. 排除伪瓶颈：连接池

现象：写接口在 16 并发时 138 req/s，加到 32 并发只有 147 req/s，延迟从 112ms 翻到 208ms。**吞吐不涨、延迟翻倍 = 请求在排队。**

第一嫌疑是 HikariCP 默认 10 个连接。

| 配置 | 读 QPS | 写 QPS | 写 P99 |
|---|---|---|---|
| `maximum-pool-size: 10`（默认） | 1193 | 138 | 219ms |
| `maximum-pool-size: 20` | 1180 | **138** | 164ms |

**完全没变。** 排除连接池。

> 连接池配置保留在 `application.yml` 里并加了注释，因为 20 对生产更合理；但这次它确实不是瓶颈，不能把它写进「优化成果」。

---

## 3. 排除伪瓶颈：SQL 控制台日志

`application.yml` 原本是：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
```

`StdOutImpl` 每条 SQL 都 `System.out.println`，压测时是同步 IO + 大量字符串拼接。改成 `Slf4jImpl`、级别设 info（默认不打）：

| 指标 | StdOutImpl | Slf4jImpl |
|---|---|---|
| 读 QPS | 1180 | **1646（+40%）** |
| 读 P50 | 16.9ms | **9.1ms** |
| 写 QPS | 138 | 139 |

读接口涨了 40%，写接口没动。所以**日志是读接口的一部分开销，但不是写接口的瓶颈**。

这个改动本身值得保留：生产环境把每条 SQL 打到 `System.out` 是坏习惯，既慢又会把日志文件撑爆。

## 4. 排除伪瓶颈：Python 客户端的 GIL

写接口卡在 139 req/s，但单请求只要 7.6ms——按这个算，单线程就该有 131 QPS。16 个线程加起来还是 139，等于**并发没有产生任何收益**。

这不像服务端行为，更像采样工具被打满了。Python 有 GIL，多线程压测时 JSON 编解码和数据拷贝会串行。

用多进程（每个进程独立 GIL）验证：

| 场景 | 1 进程 | 4 进程 | 8 进程 |
|---|---|---|---|
| 商品列表 | 324 req/s | 1339 req/s（4.1×） | **2379 req/s（7.3×）** |
| 下单 | 88 req/s | 139 req/s（1.6×） | 146 req/s（1.7×） |

**读接口随进程数线性扩展**，说明客户端不再是瓶颈——服务端能扛 2300+ QPS。
**写接口 4 进程后就不再增长**，说明这次是真的服务端瓶颈。

## 5. 确认真瓶颈：热点商品行锁

写接口的瓶颈在哪？所有压测请求都买**同一个商品**，而扣库存是：

```sql
UPDATE product SET stock = stock - 1, sales = sales + 1
 WHERE id = ? AND stock >= 1;
```

InnoDB 对 `id = ?` 这一行加排他锁，**同一商品的并发下单必须串行**。

验证方法：建 20 个商品，让请求轮流买不同的商品（其余条件完全一致）。

| 场景 | 吞吐 | 成功 |
|---|---|---|
| 8 进程，全部买同一商品 | 145 req/s | 640 / 640 |
| 8 进程，分散到 20 个商品 | **506 req/s（3.5×）** | 640 / 640 |

**瓶颈确认是热点行锁，不是连接池、不是日志、不是框架。**

### 这意味着什么

这是秒杀场景的经典问题：**同一个热门商品的吞吐上限 = 单行锁的持有时间决定**。真实电商的应对手段：

| 手段 | 说明 |
|---|---|
| 库存分桶 | 把 1000 件库存拆成 10 份，扣减时随机选一个桶，把单行锁变 10 行锁 |
| 预扣库存到 Redis | 请求先在 Redis 扣减，异步落库，把 MySQL 从热点路径上摘掉 |
| 队列削峰 | 请求进 MQ 串行处理，前端轮询结果 |
| 业务限制 | 单用户限购、验证码、随机丢弃部分请求 |

本项目是单体教学项目，**没有做这些优化**，因为引入 Redis/MQ 会让部署复杂度翻倍，而收益在当前规模下为零。但在简历/面试里能说清楚「瓶颈在哪、为什么现在不优化、要优化该怎么做」，比堆一堆中间件更有说服力。

## 6. 完整数据汇总

测试条件：32 并发 × 每场景 500 请求（下单场景并发减半），修复后配置。

### 读：`GET /api/products?page=1&size=10`

| 阶段 | QPS | avg | P50 | P90 | P99 |
|---|---|---|---|---|---|
| 修复前（StdOutImpl） | 1936 | 15.2ms | 13.5ms | 22.1ms | 52.8ms |
| 换雪花 ID 后 | 1193 | 25.3ms | 16.4ms | 32.2ms | 139.8ms |
| 连接池 20 | 1180 | 25.6ms | 16.9ms | 28.6ms | 155.0ms |
| 关 StdOutImpl 后 | **1646** | 18.5ms | 9.1ms | 22.5ms | 142.5ms |
| 多进程 8 个（上限探测） | **2379** | — | — | — | — |

> 前两行 QPS 波动主要来自客户端所在机器的负载，不是服务端变化。单看「StdOutImpl → Slf4jImpl」这一组（1180 → 1646）才是干净的对比。

### 写：`POST /api/orders`

| 阶段 | QPS | avg | P50 | P90 | P99 | 失败 |
|---|---|---|---|---|---|---|
| 修复前（订单号会撞） | 142 | 109ms | 109ms | 117ms | 159ms | **2** |
| 换雪花 ID 后 | 138 | 112ms | 109ms | 141ms | 219ms | 0 |
| 连接池 20 | 138 | 112ms | 111ms | 127ms | 164ms | 0 |
| 关 StdOutImpl 后 | 139 | 112ms | 108ms | 126ms | 193ms | 0 |
| 64 并发（32 进程/线程） | 147 | 208ms | 216ms | 226ms | 229ms | 0 |
| 8 进程 + 分散商品 | **506** | — | — | — | — | 0 |

### 单请求基线（单线程串行 20 次）

| 接口 | 平均 | 中位 | 最大 |
|---|---|---|---|
| 商品列表 | 1.6ms | 1.6ms | 2.6ms |
| 下单 | 7.6ms | 7.2ms | 10.8ms |

一次下单要做的事：查商品 → 原子扣库存 → 插订单 → 插明细 → 删购物车项 → 事务提交，7.6ms 属于正常范围。

## 7. 怎么复现

```bash
# 后端和 MySQL 先起来
cd backend && mvn spring-boot:run

# 全部场景，32 并发，每场景 500 次
python scripts/benchmark.py

# 只压读 / 只压写
python scripts/benchmark.py --scenario read
python scripts/benchmark.py --scenario create -c 8 -n 200
```

脚本会自动登录、创建压测专用商品、压测、删除商品。

**压测会往 `orders` / `order_item` 写入大量订单**，跑完清理：

```sql
DELETE oi FROM order_item oi JOIN orders o ON oi.order_id = o.id WHERE o.receiver_name = '压测';
DELETE FROM orders WHERE receiver_name = '压测';
DELETE FROM product WHERE name LIKE '【压测】%';
```

## 8. 这次压测最值得记住的四件事

**1. 功能测试测不出并发 bug。** 订单号冲突、超卖、重复提交，都要靠并发才能暴露。

**2. 吞吐不涨、延迟翻倍 = 排队，不一定是代码慢。** 先分清是「算得慢」还是「在等资源」，两者的优化方向完全相反。

**3. 压测工具本身会成为瓶颈。** Python 多线程受 GIL 限制，读接口从 324 涨到 2379 全靠换多进程。**测量之前先确认尺子准不准。**

**4. 热点行锁是写接口的天然上限。** 单商品 145、分散后 506，同样的代码、同样的机器，差 3.5 倍——差的是锁的粒度。
