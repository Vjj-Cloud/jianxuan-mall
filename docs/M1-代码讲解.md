# M1 代码讲解：用户注册 / 登录 / JWT 鉴权

> 这份文档记录了 M1 阶段每个文件在干什么、为什么这么设计、以及你自己踩过的坑。
> 面试前可以直接翻第 8 节的问答。

---

## 0. M1 的整体形状

M1 做了三件事，对应三条独立的链路：

### 链路一：注册

```
POST /api/auth/register  {"username":"jack","password":"123456"}
  → AuthController.register
    → @Valid 校验 DTO（用户名 3-20 位、密码 6-32 位）
    → UserService.register
        → 查重（selectCount username = ?）
        → BCrypt 加密密码
        → insert 到 user 表
    → JwtUtil.generate(id, role)   签发 token
    → UserVO.from(user)            剔除 password
  → {"code":200,"data":{"token":"eyJ...","user":{...}}}
```

### 链路二：登录

```
POST /api/auth/login
  → 按 username 查用户
  → passwordEncoder.matches(明文, 数据库里的哈希)
      ├─ 不匹配 → 401「用户名或密码错误」
      └─ 匹配   → 签发 token
```

### 链路三：带 token 访问受保护接口

```
GET /api/auth/me  Header: Authorization: Bearer eyJ...
  → JwtInterceptor.preHandle
      ├─ 没头 / 格式不对 → 401「请先登录」
      ├─ 验签失败        → 401「登录凭证无效」
      ├─ 已过期          → 401「登录已过期」
      └─ 通过 → UserContext.set(userId, role) → 放行
  → AuthController.me()
      → UserContext.getUserId()   拿到当前用户 id
      → 查库 → UserVO
  → afterCompletion → UserContext.clear()   清理
```

**核心思想**：`preHandle` 只做一件事——**把 token 翻译成"当前用户是谁"，塞进 ThreadLocal**。后面的 Controller / Service 从 ThreadLocal 取，不用每个方法都传 userId 参数。

## 1. 文件分工表

| 包 | 文件 | 职责 | 一句话 |
|---|---|---|---|
| `entity` | `User` | 数据库表映射 | 一行记录的对象形态 |
| `mapper` | `UserMapper` | 数据访问 | 继承 BaseMapper 白送 17 个方法，不写 SQL |
| `dto` | `RegisterRequest` | 注册入参 | 带校验注解，只含允许前端传的字段 |
| `dto` | `LoginRequest` | 登录入参 | 同上 |
| `dto` | `UserVO` | 用户出参 | 剔除 password，只给前端该看的 |
| `dto` | `LoginResponse` | 登录/注册出参 | token + UserVO |
| `config` | `PasswordConfig` | 注册 BCrypt Bean | 编码器全局唯一 |
| `config` | `WebConfig` | 注册拦截器 | 定义哪些路径要鉴权 |
| `util` | `JwtUtil` | 签发 / 解析 token | 唯一碰密钥的地方 |
| `interceptor` | `JwtInterceptor` | 校验 token | 把 token 变成 ThreadLocal |
| `common` | `UserContext` | 当前用户上下文 | ThreadLocal 的包装 |
| `service` | `UserService` | 注册 / 登录业务 | 事务外唯一该写业务逻辑的地方 |
| `controller` | `AuthController` | 三个接口 | 只做参数接收和结果包装 |

**一句话记住分层规则**：

- Controller **不写业务逻辑**，只做"收参数 → 调 Service → 包 Result"
- Service **不碰 HTTP**（不出现 HttpServletRequest / Result），只写业务
- Mapper **不写判断**，只做数据访问

这样分层的好处：Service 可以被定时任务、消息消费者复用；写单元测试时不用启动 Web 容器。

## 2. 建表：7 个字段每个都有理由

```sql
CREATE TABLE `user` (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  username   VARCHAR(50)  NOT NULL,
  password   VARCHAR(100) NOT NULL,
  nickname   VARCHAR(50)  NOT NULL DEFAULT '',
  role       VARCHAR(20)  NOT NULL DEFAULT 'USER',
  created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY UK_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

| 设计 | 原因 | 面试追问 |
|---|---|---|
| `BIGINT` 主键 | `INT` 上限 21 亿，电商订单量容易超 | 为什么不用 UUID？→ 自增是顺序写，B+ 树友好；UUID 随机写导致页分裂 |
| `UNIQUE KEY UK_username` | **并发重复注册的最后防线** | 见第 5 节「两次查重」 |
| `password` 长度 100 | BCrypt 固定 60 字符，留余量 | BCrypt 哈希里 `$2a$10$` 的 `10` 是 cost，每 +1 耗时翻倍 |
| `role` 存字符串 | 占空间但 `USER`/`ADMIN` 一眼看懂 | 什么时候用枚举？值固定且少、且需要类型安全时 |
| `created_at` 用 DB 默认值 | 应用代码可能漏设，数据库兜底最可靠 | 为什么不交给 Java？→ 见上 |
| `ENGINE=InnoDB` | **必须**：事务 + 行锁，M4 防超卖全靠它 | MyISAM 为什么不行？表锁、无事务，扣库存会超卖 |
| `utf8mb4` | `utf8` 存不了 emoji，昵称带 😀 直接报错 | —— |

**刻意没做的事**：没加 `deleted` 逻辑删除字段。用户注销不在需求里，**不为想象中的需求设计**。

## 3. Entity 与 MyBatis-Plus

```java
@Data
@TableName("user")
public class User {
    @TableId(type = IdType.AUTO)
    private Long id;
    private String username;
    private String password;
    private String nickname;
    private String role;
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
}
```

### 三个注解

| 注解 | 作用 | 不写会怎样 |
|---|---|---|
| `@TableName("user")` | 指定表名 | MP 默认找 `User` 表（大小写敏感时找不到） |
| `@TableId(type = AUTO)` | 主键自增 + 回填 | 插入后 `user.getId()` 是 null |
| `@Data` | 生成 getter/setter | MP 注不进值，查出来全是 null |

### `createdAt` 怎么对上 `created_at` 的

靠 `application.yml` 这一行：

```yaml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # created_at ↔ createdAt
```

**规则是逐字对应**：`created_at` → `createdAt`（有 d）。写成 `createAt` 会去找 `create_at` 这个不存在的列，报 `Unknown column 'create_at'`。

### 为什么主键用 `Long` 不用 `long`

`long` 默认值是 `0`，无法区分"还没入库"和"id 真的是 0"。`Long` 可以是 `null`，语义明确。

MP 的 `IdType.AUTO` 也是靠 `id == null` 判断"这是新增，不要带 id 列"。

**规则**：实体类字段一律用包装类型（`Long` / `Integer` / `BigDecimal`），只有循环变量才用基本类型。

## 4. 为什么要 DTO 这一层

### 反面教材：直接用 Entity 收参数

```java
public Result<?> register(User user) { ... }   // ❌
```

前端多发一个字段：

```json
{ "username":"jack", "password":"123456", "role":"ADMIN" }
```

Spring 会把 `role` 也绑上 → **任何人注册都能自封管理员**。

这类漏洞叫 **Mass Assignment（批量赋值）**，真实存在且常见。防御方式就是 DTO：只声明允许前端传的字段。

### 反面教材二：直接返回 Entity

```java
return Result.ok(user);   // ❌ password 被 Jackson 序列化出去了
```

响应里会出现：

```json
"password": "$2a$10$z7/h1cmqrLch95YCR9CB7OX1LPbqGzcnjG7N4ivwlq5iy2gnO3gI6"
```

哈希不能反推明文，但攻击者可以**离线暴力破解**（拿到哈希在自己机器上慢慢跑，不受服务器限流）。所以密码哈希永远不出现在响应里。

**三层数据模型**：

| 层 | 类 | 用途 |
|---|---|---|
| Entity | `User` | 数据库一行记录，含密码 |
| DTO | `RegisterRequest` / `LoginRequest` | 前端传进来的 |
| VO | `UserVO` | 给前端看的 |

看着啰嗦，但这是"防止误用"的标准做法。字段少的时候可以省，一旦表字段多了（商品有 20 个字段），不隔离必然出事。

## 5. `UserService`：两个核心逻辑

### 注册：两次查重不是冗余

```java
// 第一层：插入前查重
Long count = userMapper.selectCount(
        new LambdaQueryWrapper<User>().eq(User::getUsername, req.getUsername()));
if (count != null && count > 0) {
    throw new BusinessException("用户名已被注册");
}

// 第二层：数据库唯一索引兜底
try {
    userMapper.insert(user);
} catch (DuplicateKeyException e) {
    throw new BusinessException("用户名已被注册");
}
```

**为什么需要两层**：

```
时刻 T1：请求 A 查重 → 没查到 jack，准备插入
时刻 T2：请求 B 查重 → 也没查到 jack，准备插入
时刻 T3：A 插入成功
时刻 T4：B 插入 → 如果没唯一索引，会产生两条 jack
```

只靠第一层，高并发下必然出现重复数据。**唯一索引是数据库层面的强约束，谁都绕不过**。但只靠第二层，正常情况（99.9%）也要靠抛异常来控制流程，不优雅。

**两层配合**才是工业级写法。面试问"怎么防重复注册"，答这个结构。

### 登录：提示为什么故意模糊

```java
if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPassword())) {
    throw new BusinessException(401, "用户名或密码错误");
}
```

如果分开提示：

- "用户不存在" → 攻击者知道这个用户名**没注册**
- "密码错误" → 攻击者知道这个用户名**存在**

批量试一遍就能筛出真实用户名清单，这叫**用户名枚举攻击**。统一成一句话，攻击者什么都得不到。

**代价**：用户输错时会困惑"是用户名错了还是密码错了"。**安全优先**，业界标准取舍。

### 为什么注册不加 `@Transactional`

只插一张表、一条记录。单条 SQL 本身原子，加事务只有开销没有收益。

**什么时候必须加**：M4 下单时同时写 `order` + `order_item` + 扣库存，三步要么全成要么全败，那时候不加就会产生脏数据。

## 6. BCrypt：密码到底怎么存的

```
明文 "123456"
  → 自动生成随机盐 + 哈希 10 轮
  → "$2a$10$z7/h1cmqrLch95YCR9CB7OX1LPbqGzcnjG7N4ivwlq5iy2gnO3gI6"
```

### 三个关键事实

**① 同一个密码每次 encode 结果都不同**（盐不同）。所以不能用 `equals` 比对，必须用 `matches(明文, 哈希)`——它会把盐从哈希里解析出来再算一遍。

**② 哈希里带了盐**。`$2a$` 是版本，`10` 是 cost（计算轮数，2^10 次），后面是盐+哈希。

**③ 故意慢**。cost=10 大约 100ms。正常登录感受不到，但暴力破解的成本暴涨：攻击者每秒只能试 10 个密码，而不是 MD5 的几十亿个。

### 为什么不能用 MD5

| 算法 | 速度 | 盐 | 破解成本 |
|---|---|---|---|
| 明文 | —— | —— | 拖库即失守 |
| MD5 | 极快（每秒几十亿次） | 需手动加 | 彩虹表/GPU 暴力，分钟级 |
| BCrypt | 慢（每秒 10 次） | 内置 | 单密码数年 |

**面试标准答案**：BCrypt 内置盐（防彩虹表）+ 可调 cost（防算力进步），是密码存储的推荐算法。

### `PasswordConfig` 为什么单独建一个 Bean

```java
@Configuration
public class PasswordConfig {
    @Bean
    public BCryptPasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

直接在 Service 里 `new` 也能跑，但：cost 参数得统一、测试时无法替换成 mock、每次注入都新建实例。**交给 Spring 容器管理是标准做法**。

## 7. JWT：token 是什么

### 结构：两个点分三段

```
eyJhbGciOiJIUzM4NCJ9 . eyJzdWIiOiIyIiwicm9sZSI6IlVTRVIiLCJleHAiOjE3MzJ9 . 4kQx7...
      ① Header                    ② Payload                          ③ Signature
```

| 段 | 内容 | 能否被看到 |
|---|---|---|
| Header | 算法（HS256/HS384） | ✅ base64 解码就能看 |
| Payload | `sub`=用户id、`role`、`exp` | ✅ **谁都能解码** |
| Signature | 用密钥对前两段签名 | ❌ 没密钥算不出来 |

### 最重要的认知：JWT 是签名，不是加密

**payload 是明文可读的**，只是不能改。所以：

- ✅ 可以放：用户 id、角色、过期时间
- ❌ 绝不能放：密码、手机号、身份证号

（Payload 里那段 base64 你自己去 base64decode.org 解一下就能看到 `{"sub":"2","role":"USER"}`。）

### 为什么伪造不了

想改 `role: USER` → `ADMIN`，必须重算签名；签名需要密钥，密钥只在服务器上。改了 → 验签失败。

### 无状态的代价（面试必问）

| | Session | JWT |
|---|---|---|
| 服务端存储 | 存（内存/Redis） | 不存 |
| 多实例部署 | 要做 session 共享 | 天然支持 |
| 主动失效 | 删 session 即可 | **做不到**，只能等过期 |

**"做不到主动失效"的具体后果**：用户改了密码、管理员封号，旧 token 在过期前（我们配的 24 小时）依然有效。

**如果要解决**：引入 Redis 黑名单 → 又变成有状态了 → JWT 的优势部分丧失。这是架构取舍，不是"JWT 更好"。

### 代码要点

```java
public String generate(Long userId, String role) {
    Date now = new Date();
    return Jwts.builder()
            .subject(String.valueOf(userId))
            .claim("role", role)
            .issuedAt(now)
            .expiration(new Date(now.getTime() + expireMillis))
            .signWith(key)
            .compact();
}
```

- `Keys.hmacShaKeyFor(...)` —— 密钥**少于 32 字节直接抛 `WeakKeyException`**。这是库的安全检查，不是 bug。
- `.signWith(key)` —— 少了这行，token 就是明文 JSON。
- **版本坑**：`Jwts.parserBuilder().setSigningKey()` 是 jjwt 0.11 的写法，0.12 已删除。网上教程大量是旧版，照抄编译不过。

### 构造注入而不是 `@Autowired` 字段

```java
private final SecretKey key;
private final long expireMillis;

public JwtUtil(@Value("${jwt.secret}") String secret,
               @Value("${jwt.expire-hours}") long expireHours) { ... }
```

好处：字段是 `final`，对象创建完就完整（不会出现"半初始化"）；单元测试可以手动传参。

## 8. 拦截器 + ThreadLocal（M1 最核心）

### 拦截器 vs 过滤器

| | Filter | Interceptor |
|---|---|---|
| 规范 | Servlet | Spring MVC |
| 位置 | 更外层（DispatcherServlet 之前） | 更内层 |
| 能拿到 handler | ❌ | ✅ 能拿到"哪个方法在处理" |
| 适合 | 编码、CORS、日志埋点 | 鉴权、注解级权限 |

**关键差异**：拦截器能拿到 `handler` 参数（就是 `AuthController.me` 这个方法对象），所以以后能做 `@AdminOnly` 这种注解级控制——只在标了注解的方法上生效。Filter 做不到。

### 为什么不自己写 response，而是抛异常

```java
throw new BusinessException(401, "请先登录");
```

这一行依赖 M0 建立的三件事：

```
preHandle 抛 BusinessException
  → DispatcherServlet 捕获
  → 交给 @RestControllerAdvice
  → GlobalExceptionHandler.handleBusinessException
  → Result.fail(401, "请先登录")
```

**一行新代码都没加**，M0 的兜底机制直接复用。这就是先把基础设施设计好的回报。

### ThreadLocal：为什么必须有

Tomcat 用**线程池**处理请求，线程会被复用：

```
线程 T1：服务用户 A（userId=1）→ 处理完，线程归还池子
线程 T1：被分配给一个匿名请求 → 如果没清理，getUserId() 返回 1  ← 数据串号！
```

`UserContext` 就是给每个线程一个独立储物柜：

```java
private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();

// preHandle 里存
UserContext.set(userId, role);

// Controller 里取
Long id = UserContext.getUserId();

// afterCompletion 里必须清
UserContext.clear();   // 内部是 USER_ID.remove()
```

**为什么用 `remove()` 而不是 `set(null)`**：`set(null)` 会让 ThreadLocalMap 里保留一个 key 为 null 的 Entry，value 无法被回收 → **内存泄漏**。`remove()` 才是彻底删除。

**面试标准答案**：「ThreadLocal 配合线程池使用，必须 try-finally 里 remove，否则线程复用会导致数据串号，并且 key 弱引用被回收后 value 无法访问造成内存泄漏。」

### `afterCompletion` 一定会执行吗

- `preHandle` 返回 `true` → 后续一定调用 `afterCompletion`
- `preHandle` 返回 `false` 或抛异常 → **不会**调用

我们的代码里，抛异常的场景（token 无效）发生在 `UserContext.set` **之前**，所以没有残留风险。这个顺序是刻意设计的。

### 排除路径为什么不能写 `/api/auth/**`

```java
.excludePathPatterns(
    "/api/auth/register",   // ✅ 精确到方法
    "/api/auth/login",
    ...
)
```

如果写成 `/api/auth/**`，`/api/auth/me` 也成了公开接口 → `UserContext.getUserId()` 返回 null → `selectById(null)` 报错。

**这是权限配置里最常见的"过度放行"错误**，安全审计经常抓。原则：**默认拒绝，白名单精确到最小粒度**。

### `OPTIONS` 为什么直接放过

浏览器发跨域请求前会先发一个 `OPTIONS` 预检请求，**规范上它不带 Authorization 头**。不放过的话：

- 所有跨域请求卡在预检 → 前端报 CORS 错误
- 后端日志里**什么也看不到**（请求没进业务逻辑）

这个坑极难查，先记住。

## 9. 你在 M1 踩过的 6 个坑

| # | 错误 | 后果 | 教训 |
|---|---|---|---|
| 1 | `createAt` 少了 d | 查库报 `Unknown column 'create_at'` | 编译能过 ≠ 能跑，必须真打接口 |
| 2 | 主键用 `long` | 无法区分"未入库"和 id=0 | 实体类一律包装类型 |
| 3 | 误导入 `lombok.Value` | 报"找不到 @interface 方法 'value()'" | 同名类先查 import 的包 |
| 4 | `@Size(message=...)` 写错数字（两次） | 用户看到"用户名 6-32 位"但实际规则是 3-20 | 复制粘贴后对照 min/max 读一遍文案 |
| 5 | `User` 直接返回给前端 | BCrypt 哈希泄漏 | 必须用 VO |
| 6 | 排除路径写成 `/api/auth/**` 的冲动 | me 接口变公开 | 白名单精确到方法 |

**第 1 和第 4 条是同一类问题的两面**：一个是"名字对不上数据库"，一个是"文案对不上规则"。都是**能编译、能启动，只有真正跑起来才暴露**。

## 10. 面试八问（M1 部分）

### Q1：密码为什么用 BCrypt，不用 MD5？

BCrypt 内置随机盐（防彩虹表）+ 可调 cost（故意慢，防算力进步）。MD5 计算太快，GPU 每秒几十亿次，配合彩虹表几分钟就能反查。另外 BCrypt 的盐存在哈希串里，验证时自动解析，不用单独存盐字段。

### Q2：JWT 和 Session 的区别？

JWT 把用户信息放在 token 里，服务端无状态，天然支持多实例；代价是无法主动失效（改密码/封号后旧 token 仍有效）。Session 存在服务端，可以随时删除，但多实例要做共享（Redis）。

**选型**：内部管理后台用 Session 更简单可控；对外开放 API / 移动端用 JWT 更合适。

### Q3：JWT 的 payload 能放密码吗？

不能。JWT 是**签名**不是加密，payload 只是 base64 编码，任何人解码就能看。只能放不怕被看到的信息（用户 id、角色）。

### Q4：怎么防止重复注册？

两层：应用层 `selectCount` 查重（给友好提示）+ 数据库 `UNIQUE` 索引兜底（拦并发）。只有第一层，并发时会插入重复数据；只有第二层，正常流程要靠异常控制，不优雅。

### Q5：登录失败为什么提示"用户名或密码错误"，不分开说？

防用户名枚举攻击。分开提示等于告诉攻击者哪些用户名真实存在，他可以批量筛出用户清单再定向爆破。

### Q6：ThreadLocal 有什么坑？

线程池复用导致数据串号 —— A 用户的数据被 B 用户读到。必须在 `finally` / `afterCompletion` 里 `remove()`。另外 `set(null)` 不等于 `remove()`，后者才能避免 value 无法回收的内存泄漏。

### Q7：拦截器和过滤器（Filter）的区别？

Filter 是 Servlet 规范，在 DispatcherServlet 之前，拿不到 handler 信息；Interceptor 是 Spring MVC 的，能拿到具体处理方法，适合做鉴权、注解级权限控制。执行顺序：Filter → Interceptor.preHandle → Controller → postHandle → afterCompletion → Filter。

### Q8：token 过期了怎么办？前端怎么处理？

后端返回 `code:401`。前端 axios 响应拦截器统一捕获 401 → 清 localStorage 的 token → 跳转登录页。**不做自动刷新**（refresh token 是另一套机制，本期不做）。前端跳转时要带 `redirect` 参数，登录后回到原页面。

## 11. 三个自测练习

### 练习 1：让 token 过期，看提示对不对

`application.yml` 里把 `jwt.expire-hours` 改成 `0`（或改成负数），重启服务，登录拿 token，再访问 `/me`。

**期望**：`{"code":401,"message":"登录已过期，请重新登录"}`

**验证的是**：`ExpiredJwtException` 那个 catch 分支真的生效。改完记得改回来。

### 练习 2：改 token 里的 role，看能不能提权

1. 登录拿到 token
2. 把 payload 那段 base64 解码，改成 `{"sub":"2","role":"ADMIN"}`，再编码回去
3. 用改过的 token 访问 `/me`

**期望**：`401 登录凭证无效`（因为签名对不上了）

**验证的是**：JWT 防篡改的真实效果。你会亲眼看到"改了 payload 就验签失败"。

### 练习 3：ThreadLocal 不清理会怎样

把 `afterCompletion` 里的 `UserContext.clear()` 注释掉，然后：

```bash
# 先带 token 请求一次（让线程池里的线程沾上 userId）
curl -s http://localhost:8080/api/auth/me -H "Authorization: Bearer $TOKEN"

# 再请求一个不该需要登录的接口，看能不能拿到 userId
```

直接观察不太容易（需要一个能读 UserContext 又不需要登录的接口）。**更简单的做法**：在 `UserContext.getUserId()` 里加一行 `log.info("取 userId={}", id)`，然后连续请求，观察是否有请求拿到了不该有的 id。

这个练习的结论比代码本身重要：**能讲清"为什么会串号"，比能修好更有价值**。
