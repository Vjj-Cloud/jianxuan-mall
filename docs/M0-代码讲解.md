## 0. 先看一张全局图：一次请求到底经过了什么

```
浏览器
  │  GET /api/ping
  ▼
Tomcat（监听 8080，把 HTTP 报文解析成 Java 对象）
  ▼
Filter 链（编码、跨域……）
  ▼
DispatcherServlet（Spring MVC 的总调度器，所有请求都从这里进）
  ▼
HandlerMapping（查表：哪个方法负责 /api/ping ？→ PingController#ping）
  ▼
PingController.ping()  ← 你的业务代码在这里
  │  return Result.ok("pong")
  ▼
Jackson（把 Java 对象转成 JSON 字符串）
  ▼
HTTP 响应 {"code":200,"message":"ok","data":"pong"}
```

异常一起发生，链路会拐个弯：

```
Controller / Service 抛出异常
  ▼
DispatcherServlet 捕获（业务代码不用写 try-catch）
  ▼
GlobalExceptionHandler 按异常类型匹配对应方法
  ▼
返回统一的 Result → Jackson 转 JSON
```

**记住这个结构**：M0 的 4 个文件分别守着这条链路上的 4 个位置。

## 1. 四个文件的分工（一句话版）

| 文件 | 位置 | 一句话作用 |
|---|---|---|
| `Result.java` | 出口 | 规定「所有接口返回什么形状」 |
| `BusinessException.java` | 中途 | 业务规则不满足时，主动抛出来 |
| `GlobalExceptionHandler.java` | 兜底 | 接住所有异常，翻译成统一的 `Result` |
| `PingController.java` | 入口 | 验证上面三件套是通的 |

## 2. `Result.java`：统一返回体

### 为什么要统一

假设没有统一返回体，三个接口可能长这样：

```json
{"id":1,"name":"iPhone"}                  // 商品详情，直接返回对象
{"success":true,"token":"xxx"}            // 登录，自定义格式
"删除成功"                                  // 删除，直接字符串
```

前端每调一个接口就要写一套解析逻辑。统一成 `{code, message, data}` 之后，前端只写一个拦截器：

```js
if (res.data.code === 200) return res.data.data;
else if (res.data.code === 401) 跳登录();
else 弹提示(res.data.message);
```

### 关键点 1：泛型 `<T>`

```java
public class Result<T> { private T data; }
```

`T` 是「占位符」，用的时候才确定：

```java
Result<String> a = Result.ok("pong");            // data 是 String
Result<Product> b = Result.ok(product);          // data 是 Product
Result<List<Product>> c = Result.ok(list);       // data 是商品列表
```

好处：编译期就能发现类型错误，不用到处强转。

### 关键点 2：静态方法上那个 `<T>`

```java
public static <T> Result<T> ok() {
    return new Result<>(200, "ok", null);
}
```

`ok()` 没有参数，编译器无从推断 `T` 是什么。方法签名里写 `<T>` 相当于告诉编译器：
「T 由调用方决定，你别管」。调用方写 `Result<String> r = Result.ok();` 时，T 就被定成 String。

如果漏写，返回类型会退化成 `Result<Object>`，赋值给 `Result<String>` 直接编译报错。

### 关键点 3：构造函数 private + 静态工厂

```java
private Result(int code, String message, T data) { ... }
```

外部只能 `Result.ok(...)` / `Result.fail(...)`，不能 `new Result<>(999, "随便写的", null)`。
**用 API 的形状约束住别人乱用**，这是「设计」而不是「能跑」。

### 关键点 4：`@Data`

Lombok 在**编译期**生成 `getCode()`、`setCode()`、`toString()`、`equals()`。
源码里你看不到这些方法，但 `.class` 文件里有。IDEA 里按 `Ctrl+F12` 能看到生成的方法。

## 3. `BusinessException.java`：业务异常

### 区分两类错误

| 类型 | 例子 | 谁的问题 | 日志级别 |
|---|---|---|---|
| 业务异常 | 库存不足、用户名已存在、订单不能取消 | 用户的输入 / 业务规则 | `warn` |
| 系统异常 | 空指针、数据库连不上、第三方超时 | 程序员 / 环境 | `error` + 堆栈 |

两者的处理方式完全不同：业务异常是**预期内**的，要提示用户；系统异常是**故障**，要报警给人看。

### 为什么继承 `RuntimeException` 而不是 `Exception`

Java 的异常分两类：

- **受检异常**（继承 `Exception`）：方法必须 `throws` 声明，调用方必须 `try-catch` 或继续声明
- **非受检异常**（继承 `RuntimeException`）：不强制处理，可以一路往上抛

如果 `BusinessException` 继承 `Exception`，那么从 Service 抛出的每一层方法签名都要写 `throws BusinessException`，Controller 也得写，代码全是噪音。

继承 `RuntimeException` 后：Service 里直接 `throw new BusinessException("库存不足")`，一路冒泡到 `GlobalExceptionHandler`，中间零成本。

> 这也是 Spring 的设计哲学：`@Transactional` 默认只对 `RuntimeException` 回滚，就是因为业务失败通常是「运行时」语义。

### `this(400, message)` 是什么

```java
public BusinessException(String message) {
    this(400, message);   // 调用本类的另一个构造方法
}
```

构造方法复用，避免重复写 `super(message); this.code = 400;`。

## 4. `GlobalExceptionHandler.java`：全局兜底

### `@RestControllerAdvice` 为什么能「全局」

它不是魔法，是 Spring 启动时做的三件事：

1. 扫描到带 `@RestControllerAdvice` 的类，注册成一个 Bean
2. 把这个类里所有 `@ExceptionHandler` 方法登记到一张「异常类型 → 处理方法」的表里
3. `DispatcherServlet` 捕获到异常时，查这张表，找到最匹配的方法执行

「最匹配」= 继承关系最近的。所以：

```
抛 BusinessException
  ├─ 有 handler(BusinessException) → 用它 ✅
  └─ 没匹配到 → 往上找 handler(Exception) → 用它
```

`Exception.class` 的兜底方法**不会抢走**更具体的异常，因为匹配时优先选最精确的类型。

### 四个 handler 的分工

| handler | 触发场景 | 返回 code |
|---|---|---|
| `BusinessException` | 业务规则不满足 | 异常自带的（默认 400） |
| `MethodArgumentNotValidException` | `@Valid` 校验失败 | 400 |
| `NoResourceFoundException` | 访问了不存在的路径 | 404 |
| `Exception` | 其他一切意外 | 500 |

### 为什么 404 抛的是 `NoResourceFoundException`

Spring 6.1 之后，没匹配到 Controller 的请求会落到「静态资源处理器」上，它找不到文件就抛 `NoResourceFoundException`。
老教程里写的 `NoHandlerFoundException` 在新版本里基本不会出现了 —— 这是版本差异，不是你写错了。

### 为什么兜底不返回堆栈

如果直接把 `e.printStackTrace()` 的内容返回给前端，会泄漏：

- 项目用了什么框架、什么版本（攻击者据此找对应 CVE）
- 数据库表名、字段名（据此构造 SQL 注入）
- 内部类名、包结构（据此推测架构）

正确做法：**堆栈进日志，前端只看到一句人话**。
`log.error("未捕获异常", e)` 会把完整堆栈打进控制台/日志文件，运维能看到，攻击者看不到。

### 一个刻意的设计：HTTP 状态码仍是 200

`@RestControllerAdvice` 返回对象时，HTTP 状态码默认 200，真正的错误码在 body 的 `code` 里。

好处：前端统一在 `then` 里处理，不用区分 `catch` 分支。
代价：不符合 REST 语义，用 curl / 监控工具看状态码都是 200。

这是业界常见权衡（国内大厂普遍这么干）。**面试被问到要能说出取舍**，别只会说「教程这么写的」。

## 5. `PingController.java`：入口

```java
@RestController            // = @Controller + @ResponseBody
@RequestMapping("/api")    // 类级前缀
public class PingController {
    @GetMapping("/ping")   // 方法级路径，完整路径 = /api/ping
    public Result<String> ping() { return Result.ok("pong"); }
}
```

- `@RestController` 里的 `@ResponseBody` 是关键：告诉 Spring「方法返回值不要去找页面模板，直接序列化成 JSON 写进响应体」
- 路径是**拼接**的：类上 `/api` + 方法上 `/ping` = `/api/ping`
- `Result<String>` 让 `ok("pong")` 的 `T` 推断成 `String`

## 6. 常见报错对照表

| 现象 | 原因 | 怎么修 |
|---|---|---|
| `找不到符号: 类 Result` | 没 import | `Alt+Enter` 导入 `com.jack.jianxuan.common.Result` |
| 404，但接口明明写了 | 类不在启动类同包/子包下 | `BackendApplication` 在 `com.jack.jianxuan`，Controller 必须在它下面 |
| 返回的是 XML 不是 JSON | 缺 Jackson 依赖 | 本项目 `spring-boot-starter-web` 已带，检查是否被 exclude |
| `@Data` 报错找不到 getter | Lombok 没生效 | 装 Lombok 插件 + 开启 Annotation Processing |
| 启动报 `Port 8080 was already in use` | 上次进程没退 | 任务管理器结束 `java.exe`，或改端口 |
| 中文乱码 | 响应编码 | Spring Boot 3 默认 UTF-8，一般不会；检查 IDE 文件编码 |

## 7. 面试四问（参考答案）

**Q1：为什么要统一返回体？HTTP 200 + 业务 code 和直接用 HTTP 状态码，各有什么取舍？**

统一返回体让前端只需一套解析逻辑；HTTP 状态码语义更标准，但错误信息表达力有限（400 说不清是哪个字段错），而且网关、CDN、浏览器对非 2xx 的处理各不相同。我们选 body 带 code、HTTP 恒 200，代价是不符合 REST 语义、监控看状态码失真。

**Q2：`@RestControllerAdvice` 的原理？**

启动时被扫描注册为 Bean，其 `@ExceptionHandler` 方法被登记进异常处理器映射表；`DispatcherServlet` 捕获异常后由 `ExceptionHandlerExceptionResolver` 按类型最精确匹配，反射调用对应方法，返回值经 `HttpMessageConverter` 序列化成 JSON。

**Q3：为什么兜底异常不把堆栈返回前端？**

堆栈会泄漏框架版本、表结构、包结构，等于给攻击者画系统地图；同时暴露内部实现细节也不专业。正确做法是日志里记完整堆栈，前端只给通用提示 + 唯一 traceId 便于对账。

**Q4：`BusinessException` 为什么不直接用 `RuntimeException`？**

需要携带业务错误码，让前端能按 code 分支处理（401 跳登录、403 提示无权限）；直接抛 `RuntimeException` 只能靠 message 字符串区分，脆弱且不可维护。自定义异常还能让全局处理器精确拦截，不影响真正的系统异常。
