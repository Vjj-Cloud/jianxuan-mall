# M8 · 商品详情缓存（Redis + Cache-Aside）

> 记录设计取舍与实测数据。缓存这块面试问得最多，而多数人只能背「穿透击穿雪崩」三个词，
> 讲不清「为什么是这个方案」。本文的每一节都按「选了什么 / 为什么不选另一个」来写。

---

## 一、缓什么、不缓什么

| 对象 | 是否缓存 | 理由 |
|---|---|---|
| 商品详情 `GET /api/products/{id}` | ✅ 30 分钟 + 随机抖动 | 一个 id 一个 key，访问集中在少数热门商品，收益最直接 |
| 分类列表 `GET /api/categories` | ✅ 1 小时 + 随机抖动 | 「读极多、写几乎为零」，每个列表页都要用它把 categoryId 翻成名字 |
| 商品列表 `GET /api/products?page=&keyword=&sort=` | ❌ 不缓存 | 见下 |

**为什么不缓存商品列表**：key 由「关键字 + 分类 + 排序 + 页码 + 页大小」组合而成，
组合数远大于实际访问量，命中率低；每个组合都要占内存，还很难做过期管理。
缓存要解决的是「访问模式稳定的热点」，不是「所有查询」。列表本身是一条带索引的分页查询，
在数据量不大时数据库完全扛得住（压测 500+ QPS 时列表接口不是瓶颈）。

> 判断标准：**能不能说出「这个 key 一天被读多少次、写多少次」**。说不出来就别缓存。

## 二、Cache-Aside：读时填、写时删

```
读：查 Redis → 命中直接返回
              → 未命中：查库 → 回填 Redis → 返回

写：改库 → 删 Redis
```

### 为什么是「删缓存」而不是「更新缓存」

假设缓存里存的是整个商品 VO。两个管理员几乎同时改同一个商品：

```
线程 A：改库(name=X) ────────────────► 更新缓存(name=X)
线程 B：      改库(name=Y) ──► 更新缓存(name=Y)
```

A 的「更新缓存」如果晚于 B 执行，缓存里最终是 X，而数据库里是 Y——**缓存永久是错的**，
因为之后没有任何动作会纠正它（TTL 到期前一直是脏的）。

删除就不存在这个问题：删除是幂等的、不依赖顺序，删完之后下一次读一定回源拿到最新值。
**「更新缓存」是在缓存里做写操作，「删除缓存」是把一致性责任交给下一次读——后者简单得多。**

### 为什么是「先更库、再删缓存」，而不是反过来

如果先删缓存、再更库：

```
删除缓存 ──(窗口期)── 更库生效
              ↑
        这期间来的读请求：缓存空了 → 回源读到「旧值」→ 写回缓存
```

写回之后，再没有任何删除动作，缓存就一直停留在旧值。

先更库再删，最坏情况也只是一种极窄的时序：读请求在「更库之前」回源拿到旧值、
在「删缓存之后」才写回。窗口是微秒级，而且可以用「延迟双删」（更新后过 500ms 再删一次）
兜住。本项目没有采用延迟双删——它本质是在赌第二次删除能覆盖掉那个窗口，
代价是每个写操作多一次延迟和一次 Redis 调用，收益和成本不成比例。

### 删缓存失败了怎么办

当前实现只打 warn 日志，靠 30 分钟 TTL 自然过期兜底。这是个**真实的可靠性缺口**，
不打算藏：缓存最多脏 30 分钟。

彻底的做法有两条路：
1. 删缓存放进重试队列（RocketMQ 延迟重试 / 本地消息表），失败了几秒后重删；
2. 订阅 MySQL binlog（Canal），由独立进程负责失效——业务代码完全不用管缓存。

本项目量级不值得上第二个组件，但要知道这个缺口存在。

## 三、三个经典问题，逐条对应实现

### 1. 穿透：查一个根本不存在的 id

**问题**：`GET /api/products/99999999`，缓存永远不命中，每次都打到数据库。被人用随机
id 刷接口时，数据库白扛全部流量。

**方案**：把「不存在」也当成一种查询结果缓存起来。

```java
// ProductCache#loadAndCache
catch (BusinessException e) {
    if (e.getCode() == 404) {
        setQuietly(key, "__NULL__", 60);   // 60 秒
    }
    throw e;
}
```

读到 `__NULL__` 直接抛 404，不碰数据库。TTL 取 60 秒而不是 30 分钟，是为了避免
「商品刚上架却一直 404」。

**为什么不用布隆过滤器**：布隆过滤器要维护全量 id 集合（启动时预热或增量同步）、
新增商品要写入、删除商品只能靠误判率兜着（布隆不支持删除），还要引入 RedisBloom 模块。
本项目的 id 空间只有十几个，一个占位字符串就够了。
**方案要和数据规模匹配**——这句话本身就是面试答案的一部分。

### 2. 击穿：热点 key 刚过期，N 个请求同时回源

**问题**：某个热门商品缓存到期的那一刻，100 个并发请求全部未命中，同时去查库。

**方案**：SETNX 抢锁，只有抢到锁的线程查库重建，其余线程等 50ms 后重读缓存。

```java
String token = UUID.randomUUID().toString();
if (!tryLock(lockKey, token)) {          // setIfAbsent(key, token, 3s)
    sleep(50);
    // 重读缓存，大概率已经有值了；实在没有才直查库
}
try {
    // 双重检查：等锁期间可能已经有人重建完
    ...
} finally {
    unlock(lockKey, token);              // Lua 比对 token 后再 DEL
}
```

**释放锁为什么要用 Lua 比对 token**：线程 A 持锁期间卡顿超过 3 秒，锁自动过期，
线程 B 拿到新锁。此时 A 恢复执行并直接 `DEL`，删掉的是 B 的锁——B 的重建还没完成，
锁就被「偷走」了，互斥失效。把「比对 value + 删除」放进同一个 Lua，两步之间插不进命令。

**为什么不用「逻辑过期」**：逻辑过期是 value 里存一个过期时间，读到已过期的数据时
返回旧值 + 异步重建。好处是请求永不阻塞，坏处是**会短暂返回陈旧数据**，还要多封装一层
value 结构。商品价格、库存这类数据，返回旧值的风险比等 50ms 高——所以这里选了会短暂
阻塞的互斥锁。这是典型的「一致性 vs 可用性」取舍，没有标准答案，能说清就行。

### 3. 雪崩：同一批 key 同时过期

**问题**：缓存预热时批量写入的 key TTL 都一样，到点集体失效，数据库瞬间被打穿。

**方案**：TTL 加 0~300 秒随机偏移。

```java
long ttl = DETAIL_TTL_SECONDS + ThreadLocalRandom.current().nextInt(300);
```

注意：空值缓存（60 秒）没加抖动——它是零散写入的，不会形成集体过期；
而且延长空值 TTL 反而会让「刚上架的商品」更久不可见。

## 四、库存字段：缓存和写操作撞在一起（本节最值得看）

商品详情里有 `stock`（库存）和 `sales`（销量），而**每笔订单都会改这两个字段**。
如果只做「读缓存、写商品时删缓存」，就会出现：

```
用户 A 下单买了 1 件 → 库存 100 → 99
用户 B 打开商品页 → 命中缓存 → 看到库存 100
用户 B 下单 → 提示库存不足（或者更糟：超卖）
```

**处理方式**：下单扣库存、取消回补库存之后，都删掉对应商品的详情缓存。
`OrderService` 里三处调用点：`create()` 的 afterCommit、`cancel()`、`cancelBySystem()`，
统一走 `ProductCacheEvictor`。

### 删缓存的时机：必须在事务提交之后（这条一开始写错了）

库存回补是在事务里执行的 UPDATE，提交前对其他连接不可见。如果这时就把缓存删了：

```
 T1（取消订单，事务中）        T2（读商品详情）
 ├─ UPDATE stock = stock + 1    │
 ├─ DEL cache:product:1         │
 │                        ├─ 缓存未命中 → 回源，读到未提交的旧库存
 │                        └─ 把旧库存写回缓存（TTL 30 分钟）
 └─ COMMIT
```

提交之后库存已经是新值，但缓存里是旧值，**30 分钟内没有人会纠正它**。
原始代码在方法体末尾直接 `evict`，理由写的是「事务回滚时库存没变，所以删了也没事」——
这句话只考虑了回滚，漏掉了并发。

正确做法是 `ProductCacheEvictor.evictAfterCommit()`：注册 `TransactionSynchronization`，
只在提交成功后删；再**延迟 1 秒补删一次**（延迟双删），清掉那个「慢半拍的读请求」回填的旧值。
补偿删除用单线程守护调度器执行，异常一律吞掉——走到这一步订单已经成功，
不能因为 Redis 报错让接口返回 500。

> 细节坑：`afterCommit` 回调里不要再调 `evictAfterCommit`（此时同步器仍激活，
> 新注册的永远不会被回调），要用 `evictNow`。详见 [`M10-代码评审修复.md`](M10-代码评审修复.md) 第 2 条。

**代价要说清楚**：热门商品被频繁下单时，缓存会反复失效，命中率下降。

**为什么仍然这么做**：
1. 商品详情是「读远多于写」的场景，浏览与下单的比例通常是几十比一，删缓存不会击穿整体命中率；
2. 库存准确性 > 缓存命中率。宁可多用一次缓存，也不能让用户看到错误库存。

**如果哪天量级到了「下单频率高到缓存基本用不上」怎么办**：
正确做法不是停止删缓存，而是**把库存从商品详情里拆出去**——
详情页只缓存静态字段（名称、价格、描述、封面，这些几乎不变），
库存单独做一个短 TTL 或实时查库的接口。
这样详情缓存可以很长（几小时），库存永远是准的。

> 这条演进路径能讲清楚，比一上来就上复杂方案更有说服力。

## 五、Redis 挂了怎么办（降级与熔断）

缓存是性能组件，不能变成单点故障。所有 Redis 调用都包了 try/catch，
失败时降级为直查数据库。但**只做降级还不够**——第一次实测时发现：

```
Redis 停机，请求商品详情：耗时 10.05 秒
```

原因是一次详情请求要碰三次缓存（读缓存、抢锁、回写），每次都要等连接超时，
串行累加就是好几秒。接口返回 200，但已经慢到不可用。

**处理**：
1. `application.yml` 的命令超时从 2000ms 收到 **500ms**（同机 Redis 正常耗时 <1ms，500ms 已极宽松）；
2. 加一个极简熔断器 `CacheHealth`：任何一次 Redis 操作失败后，**5 秒内所有请求直接跳过缓存**。

```
private volatile long openUntil;
public boolean isOpen() { return System.currentTimeMillis() < openUntil; }
```

5 秒后自动放行 = 熔断器的「半开」状态，让下一个请求去试探 Redis 是否恢复。
一个 volatile 时间戳就够了，没必要引 Resilience4j。

**改完的实测**：

| 场景 | 改前 | 改后 |
|---|---|---|
| Redis 停机后第 1 次请求 | 10.05 s | 2.55 s |
| 停机后后续请求（熔断中） | 10.0 s | **4.3 ms** |
| Redis 恢复后 | — | 自动接回，缓存正常重建（TTL 1903） |

**要注意的副作用**：熔断期间如果有写操作（改商品），删缓存会失败。
Redis 恢复后，缓存里可能还留着旧数据直到 TTL 到期。
彻底解决同样靠 binlog 订阅——这是「不做 binlog」这个选择的连带代价。

## 六、实测记录

全部在本机实测（Redis 服务 + MySQL 8 + 后端 8080）。

| 验证项 | 方法 | 结果 |
|---|---|---|
| 首次请求写缓存 | `GET /api/products/1` 后看 key | `cache:product:detail:1` 存在，TTL **1961**（1800 + 161 抖动）|
| 缓存真的命中 | **绕过接口直接 SQL 改名**，再请求详情 | 接口仍返回旧名「星环 X1 智能手机」 ✅ 证明没查库 |
| 写操作删缓存 | 管理端 `PUT /api/admin/products/1` | key `exists=0`，再请求重建，返回新值，TTL 1967 |
| 空值缓存（防穿透） | `GET /api/products/99999` | HTTP 404，key 值为 `__NULL__`，TTL 60 |
| 分类缓存 | `GET /api/categories` | `cache:category:list` 存在，TTL 3839（3600 + 239）|
| 下单后缓存失效 | 先建缓存 → 下单商品3 ×1 | key 被删；再请求返回库存 **86**（原 87）✅ |
| 取消后缓存失效 | 取消同一订单 | key 被删；再请求库存回到 **87** ✅ |
| 击穿防护 | 清缓存后 **50 并发**打同一商品，看 `Com_select` | 增量 **3** 次（无锁应为 100 次：50 并发 × 2 条 SQL）|
| Redis 故障降级 | 停服务后请求 | 全部 HTTP 200，首次 2.55s、熔断后 4.3ms |
| 既有测试 | `mvn test` | 6 个测试全绿，无回归 |

> 「绕过接口直接改库」这个测法值得记住：只看接口返回对不对，是分不清「命中缓存」和
> 「恰好查库拿到同样的值」的；改库而接口不跟着变，才能证明它真的没查库。

## 七、面试问答

**Q1：为什么用 Cache-Aside 而不是 Read/Write Through？**
Cache-Aside 由业务代码控制读写时机，缓存层不需要和数据库耦合；Through 模式需要缓存层
自己去操作数据库（通常要自己写 CacheLoader/CacheWriter），且写穿透模式下每次写都要
同步写缓存，失败处理复杂。业务简单时 Cache-Aside 最直接。

**Q2：为什么不更新缓存而是删缓存？**
并发写时「更新缓存」的落库顺序和「改库」的顺序可能颠倒，导致缓存永久脏。
删除是幂等的，且把一致性责任推给下一次读（一定回源最新值）。

**Q3：先删缓存再更库行不行？**
不行。删完缓存、更库还没生效的窗口里，读请求回源读到旧值并写回，之后再没有删除动作，
缓存就一直是旧的。必须先更库再删。

**Q4：删缓存失败怎么办？**
当前靠 TTL 兜底（最多脏 30 分钟）。彻底方案：删缓存失败的记录进重试队列；
或订阅 binlog（Canal）由独立进程失效，业务代码不参与。

**Q5：缓存穿透、击穿、雪崩分别是什么，你怎么解决的？**
- 穿透：查不存在的数据 → 空值缓存 60 秒（未用布隆，因为 id 空间小、布隆不支持删除）
- 击穿：单个热点 key 过期 → SETNX 互斥锁 + 双重检查 + Lua 比对 token 释放
- 雪崩：大批 key 同时过期 → TTL 加 0~300 秒随机偏移

**Q6：为什么不用布隆过滤器？**
需要维护全量 id 集合、新增要同步、删除只能靠误判兜着，还要额外组件。
本项目 id 空间只有十几个，空值缓存一行代码解决。方案要匹配数据规模。

**Q7：为什么用互斥锁不用逻辑过期？**
逻辑过期不阻塞但会返回陈旧数据；商品价格/库存对准确性敏感，宁可让请求等 50ms。

**Q8：库存变了缓存怎么办？**
下单/取消后删商品详情缓存（`OrderService` 三处）。代价是热点商品缓存频繁失效，
但详情是读远多于写，且库存准确性优先。量级更大时把库存拆成独立接口，详情只缓存静态字段。

**Q9：Redis 挂了系统还能用吗？**
能。所有缓存调用 try/catch 降级直查库，再加 5 秒熔断避免每个请求串行等超时。
实测：停机后首次 2.55s、熔断期间 4.3ms、恢复后自动接回。

**Q10：怎么验证缓存真的生效了？**
不能只看接口返回对不对。做法是绕过接口直接改数据库，再请求接口——如果接口仍返回旧值，
说明它读的是缓存。另外用 `Com_select` 前后差值量化击穿防护：50 并发只打了 3 次库。

**Q11：为什么手写而不用 `@Cacheable`？**
注解表达不了 TTL 抖动、空值占位、互斥锁重建，硬做要自定义 CacheManager + KeyGenerator，
配置比代码长。手写多几十行，但每个策略都在明处，也方便按需降级。

**Q12：缓存的 key 怎么设计？**
`cache:product:detail:{id}`、`cache:category:list`、`cache:lock:product:{id}`。
统一 `cache:` 前缀便于批量排查（`SCAN cache:*`）和后续按业务清理；
命名里带上业务语义，不要用 `p:1` 这种缩写。
