# M5 代码讲解：管理端订单

> 对应提交：`feat: 管理端订单列表与发货（M5）`
> 覆盖范围：权限复用 → 列表复用重构 → 关键字 NPE → 同一个 VO 两种表现 → 发货状态机 → 实测
> 难度：**低**。两个接口，但里面藏着两处「编译不报错、只在特定请求下炸」的坑。

---

## 0. 这一模块在补什么

M4 结束时，用户能下单、能取消、能确认收货。但「发货」这个动作属于商家，用户做不了——所以订单会永远卡在 `PENDING`：

```
PENDING ──(用户取消)──> CANCELLED
   │
   └──(管理员发货)──> SHIPPED ──(用户确认收货)──> COMPLETED
            ↑
        缺的就是这一步
```

M5 就补这一步，顺带给出商家侧需要的订单列表（能看到所有用户、能按订单号搜、能按状态筛）。

两个接口：

| 接口 | 说明 |
|---|---|
| `GET /api/admin/orders?status=&keyword=&page=&size=` | 全部用户的订单，分页 |
| `PUT /api/admin/orders/{id}/ship` | 发货，仅 `PENDING` 可用 |

---

## 1. 权限：一行注解，没有新增任何代码

```java
@RestController
@RequestMapping("/api/admin/orders")
@RequiredArgsConstructor
@AdminOnly
public class OrderAdminController { ... }
```

`@AdminOnly` 贴在**类**上，`JwtInterceptor` 里那段 `getMethodAnnotation` → `getBeanType().getAnnotation` 的逻辑（M2 写的）直接生效。M5 的权限部分是零成本。

这就是 M2 把注解和检查分开的回报：**注解负责声明意图，拦截器负责执行意图**。以后加订单导出、加退款审核，只要贴同一个注解，不用碰拦截器。

## 2. 列表：为什么不能直接用 `page()`

用户端的 `page()` 第一行就写死了这个条件：

```java
.eq(Order::getUserId, userId)
```

它是越权防线——不写，用户 A 能看到用户 B 的订单。但管理端必须**不带**这个条件，否则管理员只能看到自己下的单（通常一单都没有）。

处理方式和 M2 商品那边完全一致：抽私有方法，把差异做成参数。

```java
public PageResult<OrderVO> page(Long userId, OrderQuery query) {
    return queryPage(userId, query);          // 用户端：userId 非空 → 只查自己
}

public PageResult<OrderVO> adminPage(OrderQuery query) {
    return queryPage(null, query);            // 管理端：userId 传 null → 不限制
}
```

`queryPage` 里对应的写法：

```java
.eq(userId != null, Order::getUserId, userId)
```

`eq` 的第一个参数是 `condition`，为 `false` 时这段条件**不会拼进 SQL**。所以 `userId = null` 生成的是 `SELECT ... FROM orders WHERE status = ?`，没有任何归属限制。

### 一个必须写进注释的约定

`userId = null` 在这里的含义是「不限制归属」。这是个**隐式约定**，不是类型系统能保证的东西：

- 如果哪天有人在 `page()` 里手滑写了 `queryPage(null, query)`，用户端立刻能看到所有人的订单——而且编译器不会提醒你。
- 反过来，如果 `adminPage()` 写成 `queryPage(0L, query)`，管理端会静默变成「查 userId=0 的订单」，列表永远是空的，也不报错。

所以这个方法上必须写清楚 `null` 是什么意思。**代码里凡是靠 `null` 传达语义的地方，都要用注释锁死**，否则半年后连写它的人都会犹豫。

> 更严格的写法是用两个方法：`queryMine(userId, query)` 和 `queryAll(query)`，各自拼自己的条件，重复十几行但绝对安全。这里选了共用，是因为条件完全一致、只有一行不同。**取舍标准：差异只有一行可以共用，差异超过两行就该拆开。**

## 3. 那个只在「不传关键字」时才炸的 NPE

管理端要支持按订单号搜索。最直观的写法是：

```java
.like(StringUtils.hasText(query.getKeyword()), Order::getOrderNo, query.getKeyword().trim())
```

看起来没问题——`condition` 为 `false` 时 MyBatis-Plus 会跳过这段 SQL。但这句话只对**框架**成立，对 **Java** 不成立。

`condition` 是第一个实参，`query.getKeyword().trim()` 是第三个实参。**Java 求值实参在前、调用方法在后**，也就是说在 `like(...)` 被调用之前，`trim()` 就已经执行完了。

管理端点开订单页时搜索框是空的 → `keyword == null` → 直接：

```
java.lang.NullPointerException: Cannot invoke "String.trim()" because ...
```

### 为什么这个 bug 特别难查

它的触发条件是「**不传** `keyword`」：

| 请求 | 结果 |
|---|---|
| `GET /api/admin/orders?keyword=SO2026` | 正常 |
| `GET /api/admin/orders` | **500** |

而开发时你几乎总会带着关键字测（因为你在测搜索功能本身），第一次打开页面反而没测。「测试通过」之后，用户点进来第一下就 500。

### 正确写法

```java
// 先算出值，再决定要不要用
String keyword = StringUtils.hasText(query.getKeyword()) ? query.getKeyword().trim() : null;

...
.like(keyword != null, Order::getOrderNo, keyword)
```

`keyword` 是 `null` 时，第三个实参就是 `null`——**传 null 给一个不会被使用的方法参数，是安全的**。危险的是「在一个必然执行的表达式里对可能为 null 的对象调方法」。

这条规则可以推广成一句：**凡是 `xxx.method()` 出现在参数列表里，先问一句「xxx 会不会是 null」。**

## 4. 同一个 VO，两种表现（复用 M2 的思路）

前端管理端订单表格有一列「用户ID」：

```vue
<el-table-column prop="userId" label="用户ID" width="80" />
```

但 M4 的 `OrderVO` 里**没有** `userId`，当时的注释是：

> userId 不在 VO 里：用户只能看自己的订单，把 userId 暴露出去没有任何意义

这句话对用户端完全正确，对管理端不成立——管理员需要知道「这是谁下的单」。

不用建两个 VO，加个字段 + 控制输出就行：

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
private Long userId;
```

```java
public static OrderVO from(Order order, List<OrderItem> items) {
    BeanUtils.copyProperties(order, vo, "items", "userId");   // 默认不带
    ...
}

/** 管理端专用：在用户端 VO 的基础上补上 userId */
public static OrderVO fromAdmin(Order order, List<OrderItem> items) {
    OrderVO vo = from(order, items);
    vo.setUserId(order.getUserId());
    return vo;
}
```

`@JsonInclude(NON_NULL)` 的作用是：值为 `null` 的字段**不序列化**。所以：

| 接口 | 是否输出 `userId` |
|---|---|
| `GET /api/orders`（用户端） | ❌ 没有这个 key |
| `GET /api/orders/{id}`（用户端） | ❌ |
| `GET /api/admin/orders`（管理端） | ✅ 有值 |

这是 M2 `ProductVO.status` 用过的同一个手法。**「字段该不该出现」是响应契约的一部分，不是靠前端忽略就能解决的**——多吐一个字段，就等于把「这个订单属于谁」泄露给了不该看的人。

`BeanUtils.copyProperties` 的第三个参数是**可变参数的忽略列表**：`"items"` 因为类型不同要手动转，`"userId"` 因为默认不给。

## 5. 发货：跟取消几乎一样，但有一列最容易漏

```java
@Transactional(rollbackFor = Exception.class)
public OrderVO ship(Long orderId) {
    Order order = orderMapper.selectById(orderId);
    if (order == null) throw new BusinessException(404, "订单不存在");
    if (!PENDING.equals(order.getStatus())) {
        throw new BusinessException(400, "只有待发货的订单可以发货");
    }

    LocalDateTime now = LocalDateTime.now();
    int rows = orderMapper.update(null, new LambdaUpdateWrapper<Order>()
            .eq(Order::getId, orderId)
            .eq(Order::getStatus, PENDING)       // 条件进 WHERE，防并发重复发货
            .set(Order::getStatus, SHIPPED)
            .set(Order::getShippedAt, now)       // ← 最容易漏
            .set(Order::getUpdatedAt, now));
    if (rows == 0) throw new BusinessException(400, "订单状态已变更，请刷新后重试");

    Order updated = orderMapper.selectById(orderId);
    return OrderVO.fromAdmin(updated, loadItems(List.of(orderId)).getOrDefault(orderId, List.of()));
}
```

三个点：

**① `.eq(Order::getStatus, PENDING)` 必须留在 WHERE 里。**
两个管理员同时点发货，第一个命中 1 行，第二个命中 0 行直接报错。只改 `status` 不改这个条件的话，`shipped_at` 会被第二次覆盖成更晚的时间。

**② `shippedAt` 必须手动写。**
`orders` 表的 `shipped_at` **没有** `DEFAULT CURRENT_TIMESTAMP`（只有 `created_at` 有），数据库不会帮你填。漏了这一步，接口返回 `shippedAt = null`，前端「已发货」那一行永远显示不出时间，而且没有任何报错。

> 顺便回顾 M2 那个坑：即使列上有 `DEFAULT CURRENT_TIMESTAMP`，MyBatis 插入后也不会把值读回 Java 对象。**时间字段永远手动赋值，不要依赖数据库默认值。**

**③ 改完重新查库，而不是改内存对象。**
`order.setStatus(SHIPPED)` 然后返回 `OrderVO.from(order, ...)` 也能跑。但那是「在 Java 里手写一份数据库刚做了什么的副本」——字段少时看不出问题，字段一多就会漏（比如忘了 `shippedAt`、忘了 `updatedAt`）。**一次 selectById 换一份确定正确的数据，很便宜。**

## 6. 管理端「不该有」的接口

`OrderAdminController` 只有两个方法，少了三样东西：

| 常见但没做 | 为什么不做 |
|---|---|
| 改金额 | 订单金额在用户付款时已经确定，是交易凭证 |
| 改收货地址/电话 | 同上，事后改等于伪造 |
| 删除订单 | 订单不该物理消失，只能取消（`CANCELLED`） |

这不是「功能没做完」，是**有意的边界**。订单一旦生成就是账，管理员只能推动状态（发货），不能改内容。真实电商系统里，任何对已生成订单的修改都必须留痕（操作日志 + 审批），而不是给后台开一个 `PUT /orders/{id}`。

面试时被问「订单模块你觉得还缺什么」，答「缺后台改单」是减分的，答「后台只能改状态不能改内容，因为订单是凭证」是加分的。

## 7. 实测记录

权限矩阵（`/api/admin/orders`）：

| 请求 | 结果 |
|---|---|
| 不带 token | `401 请先登录` |
| `user / user123` | `403 没有权限` |
| `admin / admin123` | `200` |
| 用户端 `/api/orders` | `200`（不受影响） |

列表：

| 场景 | 结果 |
|---|---|
| 不带任何参数 | `200`，`total=5`，**不炸 NPE** |
| 返回字段 | 含 `userId`、`items`（明细已填充，不是空数组） |
| `keyword=SO202611231259` | `total=1` |
| `keyword=20261123` | `total=5`（模糊匹配生效） |
| `keyword=不存在的单号` | `total=0` |
| `status=PENDING` | `total=1`，列表全是 PENDING |
| 用户端同样请求 | 响应里**没有** `userId` 这个 key |

发货：

| 场景 | 结果 |
|---|---|
| 用户 token 调发货 | `403 没有权限` |
| 对 PENDING 发货 | `200`，`status=SHIPPED`，`shippedAt=2026-11-23T13:03:50` |
| 再次发货 | `400 只有待发货的订单可以发货` |
| 对 CANCELLED 发货 | `400 只有待发货的订单可以发货` |
| 对 COMPLETED 发货 | `400 只有待发货的订单可以发货` |
| 订单 id 不存在 | `404 订单不存在` |
| 发货后用户端 | 看到 `SHIPPED` + 时间，`confirm` 成功变 `COMPLETED` |

完整状态机走通了：

```
PENDING ──ship──> SHIPPED ──confirm──> COMPLETED
   └──cancel──> CANCELLED（取消后不能再发货）
```

## 8. 面试自测

1. `eq(condition, column, value)` 里 `condition=false` 时，第三个参数还会被求值吗？
2. 用户端和管理端共用 `queryPage`，怎么保证用户端不会漏掉 `user_id` 条件？
3. `@JsonInclude(NON_NULL)` 和「前端忽略这个字段」有什么区别？
4. 为什么发货要用 `.eq(Order::getStatus, PENDING)` 而不是先查状态再更新？
5. 漏写 `shippedAt` 会有什么表现？为什么没有报错？
6. 为什么 `shipped_at` 不设 `DEFAULT CURRENT_TIMESTAMP` 也能工作？（提示：我们手动赋值）
7. 管理端为什么不该提供「修改订单金额」接口？
8. `@AdminOnly` 贴类上和贴方法上，拦截器的读取逻辑有什么不同？

<details>
<summary>参考答案要点</summary>

1. 会。`condition` 只控制 SQL 拼接，Java 的实参求值发生在方法调用之前。所以 `query.getKeyword().trim()` 在 keyword 为 null 时必然 NPE。
2. 靠 `queryPage` 里 `.eq(userId != null, ...)`：用户端入口 `page()` 保证 `userId` 非空，条件一定拼上。这个保证是**约定**，不是类型约束，所以必须写注释，并且 code review 时要专门盯这一行。
3. NON_NULL 是服务端根本不输出这个 key，网络传输里没有；前端忽略只是不显示，F12 里照样能看见。涉及越权信息时只有前者有效。
4. 后者是「读一次、写一次」两条语句，中间有窗口，两个请求都会读到 PENDING；前者判断和写入在同一条 UPDATE 里，靠行锁保证只有一个能成功。
5. `shippedAt` 返回 null，前端「已发货」没有时间。不报错是因为对 Java 和数据库来说都是合法值（列允许 NULL）。
6. 因为 `ship()` 里手动 `.set(Order::getShippedAt, now)`。`created_at` 有默认值是因为下单时必须带上，而 `shipped_at` 在下单时还没有意义。
7. 订单是交易凭证，金额在下单那刻就固定了（明细里还有价格快照）。后台能改金额等于能伪造交易记录。
8. `getMethodAnnotation` 只查方法本身，不会往上找类。拦截器先查方法、再查 `getBeanType().getAnnotation(...)`，两者任一存在即要求 ADMIN。
</details>

## 9. 这一模块最值得记住的三句话

**1. `condition` 能让框架跳过 SQL，不能让 Java 跳过求值。**
参数里出现 `xxx.method()`，先问 `xxx` 会不会是 null。

**2. 同一份数据面向不同角色，差异应该体现在「输出契约」上，而不是「前端要不要显示」。**
`userId` 该不该出现，由 VO 决定，不由页面决定。

**3. 管理端的能力边界是设计的一部分。**
只能推动状态、不能修改内容——这不是没做完，这是订单作为凭证的基本要求。
