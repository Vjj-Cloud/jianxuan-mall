# M3 代码讲解：购物车

> 对应提交：`feat: 购物车模块（M3）`
> 覆盖范围：建表 → 实体 / Mapper → 两个自定义 SQL → Service → VO → 5 个接口 → 前端切真实接口
> 难度：中。代码量比 M2 小，但里面藏着本项目第二个「并发正确性」问题，以及第一个「越权」问题。

---

## 0. M3 的整体形状

购物车只有一张表、一个 Service、5 个接口，但它在整个项目里的位置很特别：

```
用户点「加入购物车」
   ↓
POST /api/cart  { productId, quantity }
   ↓
JwtInterceptor      验 token → UserContext 存 userId
   ↓
CartController      从 UserContext 取 userId（不从请求参数取！）
   ↓
CartService.add()   insert 撞唯一键 → 改成原子累加
   ↓
cart_item           UNIQUE (user_id, product_id) 是最后一道防线
```

一句话概括 M3 的设计目标：**在所有可能被并发穿过的地方，都让数据库来做判断，而不是让 Java 代码判断完再去写。**

## 2. 建表：两个决定

```sql
CREATE TABLE `cart_item` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`    BIGINT UNSIGNED NOT NULL,
  `product_id` BIGINT UNSIGNED NOT NULL,
  `quantity`   INT NOT NULL DEFAULT 1,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_product` (`user_id`, `product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2.1 唯一键不是「顺手加的校验」，是并发正确性的基石

`UNIQUE KEY (user_id, product_id)` 保证「一个用户对一个商品只有一行」。没有它，第 3 节那套 `try insert / catch 累加` 就完全不成立——插入永远不会失败，购物车里会出现同一个商品的 10 行。

这条约束由 InnoDB 维护，插入检查是**原子**的：要么成功，要么抛唯一键冲突，没有「检查通过但被别人抢先插入」的中间态。

### 2.2 没建 `idx_user`

开发指南里的 DDL 还写了一个 `KEY idx_user (user_id)`，我没建。原因是**冗余**：

联合索引 `(user_id, product_id)` 的**最左前缀**就是 `user_id`，`WHERE user_id = ?` 完全能命中它。再单独建一个 `idx_user`，只会让每次写入多维护一棵 B+ 树，查不到任何额外收益。

> 这是面试里可以主动说的点：「文档这么写，但我判断是冗余索引，所以没建。」比闷头照抄更能体现你在思考。

## 3. 为什么不能「先查再插」

直觉写法：

```java
CartItem exist = cartItemMapper.selectOne(userId + productId);
if (exist == null) {
    insert(新行);
} else {
    update(exist.getQuantity() + n);
}
```

单线程完美。但用户手快，在两个标签页同时点「加入购物车」：

```
T1  请求 A: selectOne → null
T2  请求 B: selectOne → null        ← A 还没插入，B 也看到 null
T3  请求 A: insert（成功）
T4  请求 B: insert                  ← 撞唯一键（500）或插出两行（如果没唯一键）
```

两个请求都判断出「不存在」，于是都要插。**「判断」和「写入」之间有一道缝，并发就是从那道缝里钻进去的。**

正确写法在 `CartService.add()`：

```java
try {
    cartItemMapper.insert(item);          // 赌它不存在
} catch (DuplicateKeyException e) {
    // 撞了唯一键 → 说明已存在 → 改成原子累加
    int rows = cartItemMapper.increaseQuantity(userId, productId, delta, stock);
    if (rows == 0) throw new BusinessException(400, "购物车中该商品数量已达库存上限");
}
```

### 三个细节

**① 异常类型必须是 `org.springframework.dao.DuplicateKeyException`。**
MyBatis-Plus 底层走 Spring 的异常转换，MySQL 的 `SQLIntegrityConstraintViolationException` 会被翻译成它。捕获 `SQLException` 或 `Exception` 都能编译，但会顺手吞掉真正的错误。

**② `insert` 成功后自增主键会回填到 `item` 对象。** MyBatis 的 `useGeneratedKeys` 默认开启，所以 `item.getId()` 立刻可用——虽然这里没用到，但 M4 下单时会用。

**③ 这段不加 `@Transactional`。**
单条 SQL 自带原子性。如果外面包了事务，`insert` 抛异常后事务会被标记 `rollback-only`，后面的 `increaseQuantity` 也在同一个事务里，提交时会炸 `UnexpectedRollbackException`。**这是「捕获异常 + 事务」组合最常见的翻车方式。**

## 4. 把库存判断塞进 `WHERE`

`increaseQuantity` 是整个模块最值钱的一段 SQL：

```sql
UPDATE cart_item
   SET quantity   = quantity + #{delta},
       updated_at = NOW()
 WHERE user_id    = #{userId}
   AND product_id = #{productId}
   AND quantity + #{delta} <= #{stock}
```

### 为什么库存判断不能写在 Java 里

如果写成：

```java
if (exist.getQuantity() + delta <= stock) {   // 读
    update(exist.getQuantity() + delta);      // 写
}
```

「读」和「写」是两条 SQL，中间隔着一次网络往返。两个并发请求可能读到同一个 `quantity`，都判断「没超」，然后各写各的——超卖了。

放进 `WHERE` 之后，**判断和写入是同一条语句**。InnoDB 执行 UPDATE 时对目标行加行锁，锁持有期间别人改不了这一行的 `quantity`。读到的值和写回的值之间不存在时间窗口。

一句话：**判断要跟着写入一起提交给数据库，不要分批提交。**

### 返回值 `0` 的含义

| 返回值 | 含义 |
|---|---|
| `1` | 累加成功 |
| `0` | 行不存在 **或** 加完会超库存 |

在 `add()` 里调用时，行一定存在（刚刚撞了唯一键），所以 `0` 只可能是库存不够。

### 顺带：为什么手动写 `updated_at = NOW()`

M2 遇到过：`ON UPDATE CURRENT_TIMESTAMP` 在 MyBatis-Plus 显式赋值时**不会生效**，因为 UPDATE 语句里已经带了这个列，数据库认为你手动指定了值。这里手动写 `NOW()` 是显式对齐预期。

## 5. 越权：比并发更常见、更危险

`PUT /api/cart/{itemId}` 的直觉写法：

```java
CartItem item = cartItemMapper.selectById(itemId);
item.setQuantity(quantity);
cartItemMapper.updateById(item);
```

我用 `user` 的 token，把 `itemId` 改成 admin 的购物车行 id，就能改 admin 的购物车。删条目、清空同理。

**修法不是「查出来再判断 owner」，而是让 SQL 自己过滤：**

```sql
UPDATE cart_item c
  JOIN product p ON p.id = c.product_id
   SET c.quantity = #{quantity}, c.updated_at = NOW()
 WHERE c.id      = #{itemId}
   AND c.user_id = #{userId}       -- ← 关键
   AND p.status  = 1
   AND p.deleted = 0
   AND #{quantity} <= p.stock
```

`user_id` 不匹配时影响行数 0，统一按「条目不存在」处理——连「这个 id 存在不存在」都不泄露给别人。

> 术语：**IDOR（Insecure Direct Object Reference，越权访问）**，OWASP Top 10 常客。
> 修法一句话：**所有按业务主键操作的 SQL，都要带上 owner 条件。**

### `p.deleted = 0` 为什么必须手写

`@TableLogic` 只在 MyBatis-Plus **自动生成**的 SQL 里追加 `deleted = 0`。这里是自己写的 `@Update`，JOIN 进来的 `product` 表不会自动带条件。

不写这行的后果：管理端逻辑删除了一个商品，用户还能通过改数量接口把它加回购物车。

## 6. N+1 查询：购物车最容易踩的性能坑

购物车列表要显示商品名、价格、封面、分类名。最直觉的写法：

```java
for (CartItem item : items) {
    Product p = productMapper.selectById(item.getProductId());   // ← 每条一次查询
}
```

购物车 20 条就是 1 + 20 次数据库往返。首页 QPS 一高，数据库连接池直接被这种查询占满。

`CartService.toVOList()` 的做法：

```java
// 1 次：拿到所有商品
Map<Long, Product> productMap = productMapper.selectBatchIds(productIds).stream()
        .collect(Collectors.toMap(Product::getId, Function.identity()));
// 1 次：拿到所有分类名
Map<Long, String> categoryNames = categoryMapper.selectList(null).stream()
        .collect(Collectors.toMap(Category::getId, Category::getName));
```

总共 **3 次查询**（1 次 cart_item + 1 次 product IN + 1 次 category），跟购物车条目数无关。

分类表只有 5 行，直接全量查回来做 Map，比 `IN` 更省事——**小表全量查 + 内存 Map 是常见优化手段**。

## 7. 下架商品怎么处理

购物车里的商品可能在你加入之后被下架或删除。三种处理方式：

| 方案 | 表现 | 复杂度 |
|---|---|---|
| 直接过滤掉 | 商品凭空消失，用户不知道发生了什么 | 最低 |
| 返回但标记 `invalid: true` | 前端置灰显示「已失效」 | 中 |
| 下单时才校验 | 用户点到结算才被拦 | 最差 |

我选了**方案一**，和 `api.md` 的约定一致（"已下架/删除的商品不返回"），也跟前端 mock 行为一致。

代价：数据库里那行 `cart_item` 还在（`cart_item` 没有 `deleted` 列），如果用户重新上架该商品，购物车里的数量会**恢复显示**。这算一个已知的小瑕疵，可接受。

> 面试如果被问「购物车里的失效商品怎么处理」，能答出这三种方案和取舍，比只答「过滤掉」强得多。

## 8. 前端怎么切到真实接口

`src/mock/index.js` 加了开关：

```js
const MOCK_CART = false

if (MOCK_CART) {
  // ...原来的 5 个 handler
} else {
  mock.onGet(apiPath('/cart')).passThrough()
  mock.onPost(apiPath('/cart')).passThrough()
  mock.onPut(detailPath('/cart')).passThrough()
  mock.onDelete(detailPath('/cart')).passThrough()
  mock.onDelete(apiPath('/cart')).passThrough()
}
```

**为什么必须显式 `passThrough`**：axios-mock-adapter 只要注册过某个 URL 的 handler，就会拦下所有匹配请求，不会因为 handler 没返回就自动放行。`onNoMatch: 'passthrough'` 只管「完全没匹配到 handler」的情况。

**辅助函数不能删**：`userCart()` / `cartView()` / `saveCart()` 这三个函数还被订单 mock 使用（下单成功后要清空购物车）。删了前端直接白屏。

前端 store 刚好和接口返回格式对得上：

```js
async add(productId, quantity = 1) {
  this.items = await addToCart({ productId, quantity })   // 后端返回整个购物车
}
```

所有写操作返回「操作后的完整购物车」，前端拿到直接覆盖 `items`，不用再补一次 GET。这是个小设计决定：**减少一次往返，代价是响应体大一点**。购物车条目通常 < 50 条，这个取舍划算。

## 9. 实测记录

全部真跑过，不是推断。

### 9.1 权限

| 请求 | 结果 |
|---|---|
| 无 token `GET /api/cart` | `401 请先登录` |
| admin 改 user 的条目 | `404 购物车条目不存在` |
| admin 删 user 的条目 | `404 购物车条目不存在` |

### 9.2 累加与库存

| 操作 | 结果 |
|---|---|
| 加商品 1 × 2 | 购物车 1 行，数量 2 |
| 再加商品 1 × 3 | **还是 1 行**，数量 5（走唯一键分支） |
| 加商品 3 不传 quantity | 数量 1（Service 兜底） |
| 改数量为 4 | 数量 4 |
| 改数量为 0 | `400 购买数量不能小于 1` |
| 改数量为 99999（库存 88） | `400 超出库存数量，或商品已下架` |
| 加商品 1 × 99999（库存 120） | `400 超出库存数量` |

### 9.3 并发压测（最关键的一条）

用 20 个线程同时 `POST /api/cart {productId:2, quantity:1}`：

```
失败请求数 = 0
购物车行数 = 1
商品 2 数量 = 20
```

20 个请求，**0 失败、1 行、数量准确累加到 20**。如果用的是「先查再插」，这里大概率会出现唯一键 500，或者插入多行。

### 9.4 下架商品

| 操作 | 结果 |
|---|---|
| 商品 2 下架后 `GET /api/cart` | 列表里看不到商品 2 |
| 下架后 `POST /api/cart {productId:2}` | `400 商品不存在或已下架` |
| 重新上架后 `GET /api/cart` | 商品 2 带着原数量回来了 |

经 Vite 代理（5173 → 8080）实测，购物车页面拿到的是真实数据：

## 10. 面试自测

**Q1：购物车「加入商品」为什么不先查再插？**
判断和写入是两条 SQL，中间有网络往返，并发请求会同时判断出「不存在」然后各插一行。要用唯一键 + `DuplicateKeyException`，把判断交给数据库。单线程测不出来，必须压测。

**Q2：唯一键冲突被 `catch` 掉了，为什么不会导致事务问题？**
这个场景没开事务，单条 SQL 自带原子性。如果外面包了 `@Transactional`，`insert` 抛异常后事务被标记 `rollback-only`，后续操作提交会炸 `UnexpectedRollbackException`。

**Q3：库存判断为什么写在 `WHERE` 里？**
`WHERE` 的条件和 `UPDATE` 是同一个原子操作，InnoDB 会加行锁。写在 Java 里就是「读一次、写一次」，中间有窗口。

**Q4：`PUT /api/cart/{itemId}` 怎么防止改别人的购物车？**
`WHERE id = ? AND user_id = ?`，用当前登录用户的 id（来自 JWT，不是请求参数）。这叫防 IDOR。

**Q5：为什么 `p.deleted = 0` 要手写？**
`@TableLogic` 只对 MyBatis-Plus 自动生成的 SQL 生效，手写 `@Update` 里 JOIN 的表不会自动加条件。

**Q6：购物车列表怎么避免 N+1？**
`selectBatchIds` 一次 `IN` 查完所有商品，分类小表全量查回来做 Map。总查询次数固定为 3，与条目数无关。

**Q7：`itemId` 为什么不做成 `userId + productId` 拼起来的？**
前端还要用它做 `row-key`、传参，单一自增主键更简单。且唯一键已经保证了 `(user_id, product_id)` 不重复。

## 11. 下一步：M4 订单

M4 是整个项目唯一真正决定「能不能写进简历」的模块。会第一次遇到：

- **多表操作 + 事务**：一次下单要写 `order`、`order_item`、扣 `product.stock`、清 `cart_item`
- **超卖**：跟 M3 的库存判断同一个思路，但这次要跨表、跨行，还会遇到死锁
- **订单状态机**：待付款 → 已付款 → 已发货 → 已完成 / 已取消，哪些转换合法
- **金额快照**：`order_item` 必须存下单时的价格，商品改价不能影响历史订单

M3 里「把判断塞进 `WHERE`」的思路，会在扣库存时再出现一次。那次是全文最重要的 SQL。
