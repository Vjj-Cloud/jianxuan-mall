# M2 代码讲解：商品分类与商品浏览

> 对应提交：`feat: 商品分类与商品浏览接口（M2）`、`feat: 管理端商品 CRUD 与 @AdminOnly 权限校验（M2）`
> 覆盖范围：建表 → 实体 → Mapper → 分页查询 → VO → 公开接口 → `@AdminOnly` 鉴权 → 管理端 CRUD → 前端切换真实接口

---

## 0. M2 的整体形状

M2 只有两条链路，但它们是整个商城的门面——首页、列表页、详情页全都靠它们。

```
链路一：首页 / 列表页
浏览器 GET /api/products?categoryId=1&sort=priceAsc&page=1&size=12
   │
   ├─ Vite proxy 把 /api 转发到 localhost:8080
   ├─ JwtInterceptor：这是公开路径，直接放行，不校验 token
   ├─ ProductController.list(ProductQuery)
   ├─ ProductService.page()
   │     ├─ 拼 WHERE：status=1 AND (name LIKE ? OR subtitle LIKE ?) AND category_id=?
   │     ├─ 拼 ORDER BY：price ASC
   │     ├─ productMapper.selectPage → 两条 SQL（一条 COUNT，一条 LIMIT）
   │     └─ 查一次 category 全表，内存里把 categoryId 翻成 categoryName
   └─ Result<PageResult<ProductVO>> → { code:200, data:{ list, total, page, size } }

链路二：详情页
浏览器 GET /api/products/3
   ├─ ProductService.detail(3)
   │     ├─ selectById → 自动追加 deleted = 0
   │     └─ 不存在或 status != 1 → 抛 BusinessException(404)
   └─ GlobalExceptionHandler 转成 HTTP 404 + { code:404, message:"商品不存在或已下架" }
```

一个关键设计：**游客能逛，但不能买**。商品浏览接口全部在 `WebConfig` 里放行，购物车/订单接口继续被拦截器保护。

## 2. 建表：三个值得说的决定

### 2.1 金额用 `DECIMAL(10,2)`，不用 `DOUBLE`

```sql
`price` DECIMAL(10,2) NOT NULL COMMENT '售价（元）',
```

`DECIMAL(10,2)` 的意思是：总共 10 位数字，其中 2 位是小数，最大值 99999999.99。

为什么不能用 `DOUBLE`？因为 double 是二进制浮点数，它没法精确表示 0.1：

```java
System.out.println(0.1 + 0.2);        // 0.30000000000000004
System.out.println(1.0 - 0.9);        // 0.09999999999999998
```

拿这种数去算「3 件 × 29.9 元」，最后可能得到 89.69999999999999，四舍五入到分就会出现 1 分钱的偏差。电商对账差一分钱都是事故。

Java 侧对应 `BigDecimal`，不是 `double`：

```java
private BigDecimal price;
private BigDecimal originalPrice;
```

`BigDecimal` 内部是「整数 + 小数点位置」，十进制下精确。代价是运算必须用方法，不能用 `+ - * /`：

```java
BigDecimal total = price.multiply(BigDecimal.valueOf(quantity));
```

### 2.2 索引为什么是 `(status, category_id)` 这个顺序

```sql
KEY `idx_status_category` (`status`, `category_id`)
```

联合索引遵循**最左前缀原则**：只有从最左边开始连续使用列，索引才生效。

我们的查询永远是 `WHERE status = 1 AND category_id = ?`，两列都用上了，所以顺序其实可以互换。但把 `status` 放左边有两个实际好处：

1. `status` 的区分度低（只有 0 和 1），但它是**每一行都要过的过滤条件**。放最左边，MySQL 能先用它把下架商品整段切掉。
2. 只按状态查（管理端「查所有下架商品」）时，单独用 `status` 也能命中这个索引；反过来 `(category_id, status)` 就命中不了。

需要坦白一点：这个查询最后还有 `ORDER BY id DESC`，索引帮不上排序，MySQL 仍会做一次 filesort。16 条数据完全无感，但数据量上到几十万时，要么给排序字段也建索引，要么改成基于游标的分页。面试时主动说出这一点，比背「我加了索引所以很快」强得多。

### 2.3 `deleted` 逻辑删除

```sql
`deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '0 正常 / 1 已删除（逻辑删除）',
```

物理删除是 `DELETE FROM product WHERE id = 5`，删了就没了。问题是：订单表里还留着 `product_id = 5` 的记录，用户点进订单详情想看「我买的是什么」，商品已经查不到了。

逻辑删除是 `UPDATE product SET deleted = 1 WHERE id = 5`，行还在，只是标记为已删。代价是每条查询都要记得加 `AND deleted = 0`——手写一定会漏。

所以交给 MyBatis-Plus 的 `@TableLogic` 自动加。

## 3. `@TableLogic` 到底做了什么

```java
@TableLogic
private Integer deleted;
```

加上这一个注解后，三件事自动发生：

| 你调用 | 实际执行的 SQL |
|---|---|
| `selectById(16)` | `SELECT ... WHERE id = 16 AND deleted = 0` |
| `selectPage(...)` | `SELECT ... WHERE deleted = 0 AND (...你的条件...)` |
| `deleteById(16)` | `UPDATE product SET deleted = 1 WHERE id = 16 AND deleted = 0` |

实测验证过：

```
把 id=16 的 deleted 改成 1
→ 列表 total 从 16 变成 15，id=16 不在结果里
→ GET /api/products/16 返回 HTTP 404
```

注意最后一条：`detail()` 里根本没写 `deleted` 判断，它是被 `@TableLogic` 自动过滤掉的，所以 `selectById` 返回 null，代码走 `throw new BusinessException(404, ...)`。

**逻辑删除的坑**（面试常问）：
- 唯一索引会失效。比如 `UNIQUE KEY (name)`，删掉「星环 X1」后想再建一个同名商品，会撞唯一键，因为那行还在。
- 数据表会一直变大，需要定期归档。
- 每张表都要带 `deleted` 字段，别漏。

## 4. 分页插件：不注册会怎样

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
    return interceptor;
}
```

这是 M2 最容易踩的坑，因为**它的失败方式是静默的**：

不注册这个插件，`selectPage` 依然能返回数据，`list` 也是对的，但 `page.getTotal()` 永远是 0。前端分页条拿到 `total = 0`，就不显示页码了——你会以为是前端 bug，查半天。

原因：MyBatis-Plus 的分页不是靠数据库原生分页，而是靠这个拦截器在 SQL 执行前改写语句：

```
你写的：  SELECT * FROM product WHERE status = 1
拦截器改成：SELECT COUNT(*) FROM product WHERE status = 1     ← 算出 total
           SELECT * FROM product WHERE status = 1 LIMIT 0,12  ← 取出当前页
```

第二条 SQL 好写，第一条 `COUNT(*)` 必须解析你的原始 SQL 才能拼出来，解析器就是 jsqlparser。

**额外坑**：MyBatis-Plus 从 3.5.9 开始把 jsqlparser 拆成了独立依赖，光引 starter 不够，必须显式加：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-jsqlparser</artifactId>
    <version>${mybatis-plus.version}</version>
</dependency>
```

不加的表现是启动就报 `ClassNotFoundException: net.sf.jsqlparser...`，比 total=0 好排查。

## 5. `LambdaQueryWrapper`：那个括号坑

这是整个 M2 最值得讲的一段。先看代码：

```java
wrapper.eq(Product::getStatus, 1);

if (StringUtils.hasText(query.getKeyword())) {
    String keyword = query.getKeyword().trim();
    wrapper.and(w -> w.like(Product::getName, keyword)
            .or()
            .like(Product::getSubtitle, keyword));
}
```

### 错误写法会生成什么

如果贪图省事，直接链式写：

```java
wrapper.eq(Product::getStatus, 1)
       .like(Product::getName, keyword)
       .or()
       .like(Product::getSubtitle, keyword);
```

生成的 SQL 是：

```sql
WHERE status = 1 AND name LIKE '%耳机%' OR subtitle LIKE '%耳机%'
```

`AND` 的优先级高于 `OR`，所以这实际上等价于：

```sql
WHERE (status = 1 AND name LIKE '%耳机%') OR (subtitle LIKE '%耳机%')
```

后果：**只要副标题里命中关键字，下架商品也会被查出来**。商品下架了却还在搜索结果里露脸，用户点进去又是 404，体验直接崩。

### 正确写法

`and(w -> ...)` 的作用就是「把里面的条件整体用一对括号包起来」：

```sql
WHERE status = 1 AND (name LIKE '%耳机%' OR subtitle LIKE '%耳机%')
```

### 实测验证

为了确认这个括号真的起作用，我做了个对照实验：

```
1. UPDATE product SET status = 0 WHERE id = 2   （下架「声浪 Pro 无线降噪耳机」）
2. GET /api/products?keyword=空间音频   （「空间音频」只出现在它的副标题里）

正确写法结果：{"list":[],"total":0}     ← 下架商品没漏出来
错误写法结果：会出现 id=2 的商品        ← 漏了
```

这类问题叫「条件越权」或「过滤条件逃逸」。它不是语法错误，编译器不会提醒你，测试不覆盖到就永远发现不了。**写多条件 OR 查询时，第一反应就应该是加括号。**

## 6. VO 这一层的三个理由

```java
public static ProductVO from(Product product) {
    ProductVO vo = new ProductVO();
    BeanUtils.copyProperties(product, vo);
    vo.setDesc(product.getDescription());
    return vo;
}
```

为什么不直接 `return product`？

**理由一：字段过滤。** 实体里有 `status`、`deleted`。用户端不需要、也不该知道这两个字段。如果直接返回实体，前端 F12 一看就知道哪些商品被下架了。

**理由二：字段名差异。** 数据库列叫 `description`（不能叫 `desc`，那是 MySQL 的保留字），前端约定叫 `desc`。VO 是唯一适合做这层翻译的地方。

**理由三：补充计算字段。** 前端列表要显示「手机数码」，但 `product` 表里只有 `category_id`。`categoryName` 是查出来的、算出来的，不属于实体。

这也是为什么 `ProductVO.from()` 里不填 `categoryName`——它需要访问 `CategoryMapper`，那是 Service 的活。**VO 只负责字段搬运，不负责查库**，这条边界要守住。

### 顺带：`Integer` 比较的坑

```java
if (product == null || !Integer.valueOf(1).equals(product.getStatus())) {
```

不能写 `product.getStatus() != 1`。

`status` 是 `Integer`，`1` 是 `int`。写成 `!=` 时会发生自动拆箱，看起来没问题。但如果 `status` 是 `null`（比如某个历史数据没填），拆箱就 NPE。

更隐蔽的是这个：

```java
Integer a = 128;
Integer b = 128;
System.out.println(a == b);   // false ！
```

Java 的 `Integer` 缓存只覆盖 -128 ~ 127，超出范围就是两个不同对象，`==` 比的是引用地址。所以**包装类型一律用 `equals` 比较**。

## 7. 参数兜底：为什么不能信任前端

```java
private void normalize(ProductQuery query) {
    if (query.getPage() < 1) {
        query.setPage(1);
    }
    if (query.getSize() < 1) {
        query.setSize(12);
    }
    if (query.getSize() > 100) {
        query.setSize(100);
    }
}
```

三个具体的坏情况：

| 前端传 | 不兜底的后果 |
|---|---|
| `page=0` | offset = (0-1) × 12 = **-12**，MySQL 直接报语法错 |
| `page=-5` | 同上，负数 offset |
| `size=100000` | 一次性捞出全表，等于给了一条拖库的免费通道 |

这不是防「恶意攻击」那么遥远——前端自己写错分页参数、或者有人拿 Postman 随手试，都会触发。**所有从 HTTP 进来的数字，用之前都要检查范围。**

## 8. 公开接口的放行

`WebConfig` 里新增了三条：

```java
excludePathPatterns(
        "/api/auth/register",
        "/api/auth/login",
        "/api/ping",
        // 商品浏览是公开的：游客不登录也要能逛首页、看详情
        "/api/products",
        "/api/products/**",
        "/api/categories",
        ...
)
```

几个细节：

**为什么 `/api/products` 和 `/api/products/**` 都要写？** `/**` 在某些路径匹配模式下不包含「零段」的情况，两条都写上最保险，多写一行不会有副作用。

**`/api/admin/products` 会不会被误放行？** 不会。`/api/products/**` 只匹配以 `/api/products` 开头的路径，`/api/admin/products` 开头是 `/api/admin`，匹配不上。这个细节值得在面试里主动讲——放行规则写宽了，等于把管理后台裸奔。

**放行顺序**：拦截器对 `excludePathPatterns` 是「先看是否在排除列表，在就直接放过」，不进入 `preHandle`。所以游客访问商品接口时，`UserContext` 是空的。如果以后商品详情要显示「是否已收藏」，就得让这个接口变成「可选登录」——那是另一种模式（解析 token 但不强制），现在不做。

## 9. 前端怎么切到真实接口

改了一处，加了个开关：

```js
const MOCK_PRODUCT = false

if (MOCK_PRODUCT) {
  mock.onGet(apiPath('/categories')).reply(...)
  mock.onGet(apiPath('/products')).reply(...)
  mock.onGet(detailPath('/products')).reply(...)
} else {
  mock.onGet(apiPath('/categories')).passThrough()
  mock.onGet(apiPath('/products')).passThrough()
  mock.onGet(detailPath('/products')).passThrough()
}
```

**为什么必须显式 `passThrough()`？** `onNoMatch: 'passthrough'` 只对「从来没注册过 handler」的 URL 生效。只要你在某一行调用过 `mock.onGet('/products')`，mock 就会认为自己该管这个请求，不会再交给真实后端。这跟 M1 踩过的 `mock.onAny()` 是同一类问题：**注册动作本身就是一种承诺**。

保留 `if (MOCK_PRODUCT)` 分支的价值：后端挂了、或者要调纯 UI 样式时，改一个 `true` 就能退回假数据，不用去改 axios 配置。

### 封面图为什么换成本地文件

原来用 `https://picsum.photos/seed/jx-1/600/600`，是国外图床，国内网络下经常转圈不出来，演示时首页一片空白。

改成 `frontend/public/covers/{id}.svg`，16 张本地 SVG：

```html
<!-- 数据库里存的是相对路径 -->
cover = '/covers/1.svg'
```

好处：完全离线、加载 0 延迟、`vite build` 后自动进 `dist/covers/`。这也是真实项目的常见做法——图片资源走 CDN 或本地静态目录，不会把外部随机图床写进数据库。

## 12. 管理端：`@AdminOnly` 到底怎么生效

M2 上半的拦截器只验证「token 是不是真的」，不管「你是谁」。任何登录用户拿自己的 token 请求 `/api/admin/products`，都能进去。这个洞必须补。

### 12.1 注解只是贴纸，不做事

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface AdminOnly {
}
```

类体是空的，这是正确写法。注解的职责只有**声明意图**，执行意图的是拦截器。

三个元注解里，`@Retention(RUNTIME)` 是唯一不能错的：

| 级别 | 何时还在 | 典型用途 |
|---|---|---|
| `SOURCE` | 只在源码，编译丢弃 | `@Override` |
| `CLASS` | 留在 .class，运行时读不到 | 默认值，几乎没人用 |
| `RUNTIME` | 运行时可用反射读取 | **我们要的** |

写成默认的 `CLASS`，`getMethodAnnotation()` 永远返回 `null`，结果所有人都被当成非管理员，接口全 403。这个 bug 不会报错，只会让你怀疑权限逻辑写错了。

### 12.2 拦截器怎么知道「请求打到了哪个方法」

`preHandle` 的第三个参数签名是 `Object handler`，看着没信息，但它携带了「这次请求最终交给谁处理」：

- 请求 `/api/admin/products` → `HandlerMethod`，里面装着 `ProductAdminController.list()` 这个方法
- 请求 `/covers/1.svg` → `ResourceHttpRequestHandler`，没有方法
- 请求不存在的路径 → 走不到拦截器

所以第一步必须 `instanceof` 判断，否则静态资源一被请求就 `ClassCastException`。

`HandlerMethod` 提供两样东西：

| 方法 | 返回 | 用途 |
|---|---|---|
| `getMethod()` | `java.lang.reflect.Method` | 读方法上的 `@AdminOnly` |
| `getBeanType()` | `Class<?>` | 读类上的 `@AdminOnly` |

### 12.3 为什么两个都要读

```java
private boolean needAdmin(Object handler) {
    if (!(handler instanceof HandlerMethod)) {
        return false;
    }
    HandlerMethod handlerMethod = (HandlerMethod) handler;
    if (handlerMethod.getMethodAnnotation(AdminOnly.class) != null) {
        return true;
    }
    return handlerMethod.getBeanType().getAnnotation(AdminOnly.class) != null;
}
```

`getMethodAnnotation` **只查方法本身，不往上找类**。很多人的类级注解不生效就是这个原因。

本项目把 `@AdminOnly` 贴在 `ProductAdminController` 类上，一行覆盖全部 5 个接口：

```java
@AdminOnly
@RestController
@RequestMapping("/api/admin/products")
public class ProductAdminController { ... }
```

### 12.4 最关键的一行：为什么 `throw` 而不是 `return false`

```java
if (needAdmin(handler) && !"ADMIN".equals(UserContext.getRole())) {
    throw new BusinessException(403, "没有权限");
}
```

`preHandle` 返回 `false` 的含义是「我拦下了」，然后 Spring 就此结束——**不报错、不写响应体、HTTP 状态码仍然是 200**。前端拿到 200 + 空 body，`http.js` 里 `body && 'code' in body` 判断为 false，把空值原样返回，页面炸在 `data.list` 上。

抛异常才会走 `@RestControllerAdvice`，返回规范响应：

```
HTTP/1.1 403
{"code":403,"message":"没有权限","data":null}
```

**结论：拦截器里报错一律抛异常，不要 `return false`。**

### 12.5 还有一个细节：`"ADMIN".equals(...)`

```java
!"ADMIN".equals(UserContext.getRole())
```

不能写成 `UserContext.getRole().equals("ADMIN")`。如果 token 里没有 role 字段，`getRole()` 返回 null，直接 NPE。

**可能为 null 的变量做 equals 比较，常量或字面量放左边。**

## 13. 管理端 CRUD 的 4 个设计决定

### 13.1 用户端和管理端的分页怎么复用

两边唯一的差别是「要不要强制只看上架」，所以抽出一个带开关的私有方法：

```java
public PageResult<ProductVO> page(ProductQuery query) {
    return queryPage(query, true);       // 用户端：强制 status = 1
}

public PageResult<ProductVO> adminPage(ProductQuery query) {
    return queryPage(query, false);      // 管理端：按传入的 status 过滤
}

private PageResult<ProductVO> queryPage(ProductQuery query, boolean onlyOnSale) {
    if (onlyOnSale) {
        wrapper.eq(Product::getStatus, 1);
    } else if (query.getStatus() != null) {
        wrapper.eq(Product::getStatus, query.getStatus());
    }
    ...
}
```

不用复制两份，也不用在用户端方法上做 `if` 特判。

### 13.2 PUT 为什么不能加 `@Valid`

`ProductSaveRequest` 上的 `@NotBlank`、`@NotNull` 是为**新增**准备的。但 `api.md` 约定编辑接口「字段均可选，只更新传入项」：

```java
@PostMapping
public Result<ProductVO> create(@Valid @RequestBody ProductSaveRequest req) { ... }   // 有 @Valid

@PutMapping("/{id}")
public Result<ProductVO> update(@PathVariable Long id,
                                @RequestBody ProductSaveRequest req) { ... }          // 没有 @Valid
```

如果 PUT 也加 `@Valid`，前端每次改库存都得把名称、价格、分类全传一遍，接口就变成了「全量覆盖」，跟约定不符。

代价是 `update()` 里要自己判空：

```java
if (req.getName() != null) {
    if (req.getName().isBlank()) {
        throw new BusinessException(400, "商品名称不能为空");
    }
    product.setName(req.getName().trim());
}
```

注意 `isBlank()` 而不是 `isEmpty()`：`"   "` 这种全是空格的名称，`isEmpty()` 认为是合法的。

### 13.3 `status` 怎么只在管理端出现

用户端响应里不该有 `status`（只返回上架商品，这个字段没意义），管理端必须有（要显示上下架开关）。同一个 VO 两种表现，靠 `@JsonInclude`：

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
private Integer status;
```

字段为 null 时，序列化会**直接不输出这个 key**，而不是输出 `"status": null`。

`ProductVO.from()` 里也刻意排除了它：

```java
BeanUtils.copyProperties(product, vo, "status");   // 第三个参数是忽略列表
```

管理端在 `toVO(product, true)` 里手动 `vo.setStatus(...)`。

### 13.4 `updated_at` 不更新的坑

`product` 表的 `updated_at` 有 `ON UPDATE CURRENT_TIMESTAMP`，看起来不用管。但它只在**该列没有出现在 UPDATE 语句里**时才生效。

而 `updateById(product)` 传入的是 `selectById` 查出来的完整对象，`updatedAt` 是旧值，会被一起写进 SQL：

```sql
UPDATE product SET ..., updated_at = '2026-11-22 10:00:00' WHERE id = 1
```

数据库看到你显式赋了值，就不自动更新了。所以必须手动刷：

```java
product.setUpdatedAt(LocalDateTime.now());
productMapper.updateById(product);
```

实测确认：改完状态后数据库里 `updated_at` 从 `23:26:36` 变成了 `23:41:52`。

## 14. 权限与接口实测

### 14.1 权限矩阵

| 请求 | 携带 | 结果 |
|---|---|---|
| `GET /api/admin/products` | 无 token | `HTTP 401` `{"code":401,"message":"请先登录"}` |
| `GET /api/admin/products` | `user` 的 token | `HTTP 403` `{"code":403,"message":"没有权限"}` |
| `GET /api/admin/products` | `admin` 的 token | `HTTP 200`，列表含 `status` 字段 |
| `GET /api/products` | 无 token | `HTTP 200`（公开） |

### 14.2 CRUD 全流程

| 步骤 | 请求 | 结果 |
|---|---|---|
| 新增（不填封面） | `POST /api/admin/products` | `id=17`，`cover` 自动填 `/covers/0.svg`，`sales=0` |
| 用户端查新商品 | `GET /api/products/17` | 200，且**没有** `status` 字段 |
| 缺价格 | `POST` 只传 name/categoryId | `400 售价不能为空`（`@Valid` 生效） |
| 分类不存在 | `categoryId=999` | `400 商品分类不存在`（业务校验） |
| 只改库存 | `PUT {"stock":88}` | 名称、价格均未被覆盖 |
| 下架 | `PUT /17/status {"status":0}` | 用户端 detail 立即 `404`；管理端 `status=0` 列表仍能查到 |
| 删除 | `DELETE /17` | `data: null`，数据库 `deleted=1`，行还在 |
| 重复删除 | `DELETE /17` | `404 商品不存在`（`@TableLogic` 让它查不到） |
| 传非法状态 | `{"status":5}` | 被归一为 `1` |
